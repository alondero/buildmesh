# Buildmesh v1.6.1

<!-- Audience: Buildmesh users. Lifecycle: draft before the matching tag is published; historical release record afterward. -->

_2026-10-26 — 7 commits since v1.6.0 (2026-10-25)_

v1.6.1 is a **fix** release. The chrome above an agent's terminal gets out of the way, the phone can finally scroll a terminal with a finger, and a plain shell node stops claiming to be "Running" the moment you type into it.

---

## Highlights

- **The terminal gets the room back.** The full-width **Review circuit** strip that sat above every Agent Node terminal is gone — most of it repeated surfaces the card already had. Run state and review round moved into the Overview tab label (`Running · 2/5`, `2/∞` for unlimited), whose tooltip and accessible name now also carry the circuit name, the full round, the current steps and any loading or refresh-failure state. **Retry** for a failed read or refresh moved into the Overview panel, which previously showed the error with no way to retry it. The title-bar Circuit button reads **Review** as text once the header is at least 500px wide, and stays icon-only below that. Chrome above the terminal shrank from 78px to 30px on an idle card, and from 126px to 55px on a card with a running circuit; the title bar and activity tab strip are shorter too, and the header controls, tabs and banner buttons now sit on the 24px step instead of the smaller off-scale one, so they meet the documented hit-area minimum.
- **The phone can scroll a terminal by touch.** xterm.js v6 replaced its native scroll viewport with a scroller that answers the mouse wheel only — and a phone has no mouse wheel. The native Android client had no touch handling at all, so its terminal could only show the last screen of output, and less of it once the soft keyboard shrank the pane. The touch-to-scroll bridge now lives in the shared terminal owner, so the browser mobile client and the native Android client drive scrolling through one implementation and cannot drift apart. The Android pane reports when the viewport leaves or returns to the live tail and shows a **Latest** control in its app bar while it is away from the tail, so a terminal you have panned back into the scrollback can reach the running output again. The browser mobile client's scrolling behaviour is otherwise unchanged.
- **Typing in a plain shell node on the phone no longer marks it Running.** Pressing Enter in a Terminal (plain shell) node from the phone marked the node "Running" and cleared its attention. The desktop input path already skipped that lifecycle resume for plain shells; the mobile WebSocket and HTTP paths did not, and the guard had drifted apart between callers. The rule now has a single owner, shared by desktop and mobile input. The mobile "attention cleared" broadcast also fires only once a resume is actually committed, the same condition the desktop path publishes on.

---

## Upgrade notes

- **No action needed.** Every change above is applied by the update; there is no setting to change and nothing to reinstall.
- **The in-app auto-updater offers v1.6.1 to existing Windows and macOS installs as usual.** The Windows installers and the signed Android APK ship as they did in v1.6.0.
- **macOS is still early access.** The macOS builds remain ad-hoc signed with no Developer ID certificate and no notarization, so Gatekeeper blocks the first launch exactly as SmartScreen does on Windows — right-click the app, choose **Open**, then **Open** again. This release's macOS artifacts were built and audited on native runners, but the installed-app check (browser download, Gatekeeper approval, a real CLI task, session resume and the in-app update flow) was **not** run for this tag: no native Apple Silicon or Intel Mac was available. The `MACOS-INSTALLED-RECEIPT.json` attached to this release records that coverage as unverified.
- **The APK stays out of the updater feed.** `latest.json` carries the Windows and macOS desktop platforms only; the APK keeps its own `.sha256` sidecar.
- **The Android touch gesture is verified in code, not yet on a device.** The native Android client's scroll gesture is covered by an on-device instrumentation test that has not been run on a physical device or emulator yet. The browser mobile client and the shared scroll mapping are covered by the regular test suite.
