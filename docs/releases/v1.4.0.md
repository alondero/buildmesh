# Buildmesh v1.4.0

## Mobile workflow redesign

- Mobile opens with an Overview that surfaces errors, degraded status
  reporting, and agents waiting for input; each agent card names its mesh.
- Work adds search and status filters, with direct mesh Issues and Archive actions.
- Capture saves an idea draft on the phone and launches an agent with the idea
  as its initial prompt. Failed launches retain the draft.
- Agent details provide status, branch, changes, and short replies; the terminal
  remains available as an explicit action. Request text and unsent replies stay
  available while viewing changes or the terminal. Bottom navigation and touch
  controls keep common actions reachable on narrow screens.

_Draft — not yet released._

v1.4.0 is a **Circuit reliability + harness-coverage** release. Start Review
can no longer mint a run on a freshly-spawned agent that has not produced
any observable evidence; the watchdog fails fast on never-observed agents
after 15 minutes; reviewer circuits gate on whether the harness can report
its own turn completion; and a review that yields mid-work no longer
fails on the wrong turn. The harness-capability catalog work from v1.3.0
continues.

---

## Highlights

### Circuit progress and queue recovery

- Finished reports can advance circuits without requiring a complete background-task
  registry that the harness cannot provide. Session, input, report freshness, known
  unfinished work, and actual permission/question waits still guard each decision.
- Status-only input waits no longer freeze runs indefinitely. Unverified agent steps
  keep observing for fresh reports and confirmed agent loss/errors, releasing queue
  capacity when their agents disappear.
- Report-based progress remains distinct from native lifecycle verification in history;
  it does not claim proof about background work the harness cannot expose.

### Circuit evidence checkpoints (implementation in progress)

Circuit evidence timeouts can now remain at an Unverified Checkpoint. Unknown
GitHub results preserve their attempt instead of automatically repeating the
action. Expanded runs expose evidence history and reasoned operator outcomes,
with separate recheck and retry actions and stale-action protection. New runs
pin their graph for execution and recovery. The Review Blueprint can be
inspected read-only and copied into an independent, disabled manual Circuit. Review Runs also freeze effective reviewer settings;
continuations retain them across preference edits.

Codex lifecycle hooks are retained in Circuit evidence when their turn identity
does not correlate with the current input. A delayed old-turn hook is recorded as
rejected without changing the current attempt. If the completion hook is
missing, the bounded evidence window leaves the attempt Unverified with an
actionable Recheck.

An OpenPr checkpoint with a saved target can recheck that exact owner, repository,
and head branch using a read-only lookup. A match reconciles the original effect;
the check never creates another pull request. A missing or mismatched result stays
Unverified. On Windows, a live Codex Luna run confirmed exact foreground-turn
evidence and same-attempt recheck while keeping owned-work coverage Unverified.
Late-mounted terminals also filter buffered OSC 10/11 colour queries so historical
terminal replies are not replayed into live agent input.

Codex permission callbacks without a request ID now remain visible as unresolved
permission waits. Generic activity and unrelated tool results cannot grant approval
or clear them.

Antigravity (`agy 1.2.11`, Windows) `Stop` hooks now feed Circuit run history
as session-fenced turn evidence — settled versus background-busy — while
owned child/background work stays explicitly `Unverified`, since the harness
exposes no child registry and no per-turn token. A settled Antigravity turn
alone can never complete a Circuit step.

The broader reliability specification remains incomplete, including native
child/background observation, complete classifier evidence fencing, and live
human question/permission callbacks. Windows Codex Luna delivered SessionStart,
UserPromptSubmit, and Stop callbacks in a controlled app run. Claude, WSL,
Linux, and macOS were not verified in this environment. See the
[acceptance record](../development/circuit-reliability-acceptance.md).

### Named Launch Configurations

Create a proxied configuration directly from a harness's spawn submenu or Settings:
choose a credentialed provider, its model, and supported effort. Missing pairings
are saved atomically with the recipe, and Codex endpoint/model verification is
available in the editor. MiniMax's catalogue includes its Anthropic model choices
and Codex M3 thinking choices (`none` / `high`). Native harness defaults no longer
override a proxy's model default.

Native and proxied launches share named recipes grouped under each harness in
the desktop and mobile spawn menus. Known providers add compatible routes while
recipes are only the ones you save or clone, so each harness submenu starts
empty. New nodes snapshot their
resolved settings and route without credentials, so later recipe edits or
deletion do not change resume.
See [Launch Configurations](../user-guide.md#launch-configurations).
On Windows, WSL menu choices are reserved for harnesses without native Windows
support; saved WSL recipes for Windows-capable harnesses stay stored but are
hidden from spawn menus.

### Group nodes into a shared viewport

Drag a node onto another node's title or upper centre to group them as named
tabs. Drop in the lower centre to swap positions; visible drop cues preview
both actions. Groups retain review and utility tabs, can be combined or
separated again, and survive desktop restarts. See
[Group nodes into tabs](../user-guide.md#group-nodes-into-tabs).

### Hand a selection to an existing node from the terminal

The agent terminal's right-click menu can now hand its selected text to an agent
you already have running, not just to a brand-new node. **Handover to node** lists
the Mesh's other agents with the ones it already shares tabs with first — a
grouped implementer/reviewer pair sits one click apart — and each row shows the
target's status. The selection is staged as a single paste and then submitted, so
a multi-line review report arrives as one prompt rather than one prompt per line,
and a submit the harness does not take leaves the text staged in its input box
for you to press Enter on rather than losing it. See
[Hand work over to another node](../user-guide.md#hand-work-over-to-another-node).

### Clone a repository straight into a new Mesh

The **New mesh** dialog now offers **Clone from GitHub** alongside **Open
folder**. Give it an `owner/repo` or a github.com URL, pick a parent folder, and
Buildmesh clones into a new `<parent>/<repo>` subfolder and registers the Mesh in
one step — the destination path is previewed before you clone. The clone uses
your machine's existing Git authentication (SSH keys, the Git credential manager,
or `gh auth setup-git`), never a token written into the repository, and the new
Mesh's base ref is resolved to the repository's real default branch. See
[Your first session](../user-guide.md#your-first-session).

### Start Review is gated on source-agent readiness (#1792)

Pressing **Start review** on an Agent Node whose worker has not yet captured
a `cli_session_id` or read a reportable assistant revision is now refused
with a precise message:

> Source agent has not started yet — wait for its first turn before starting
> a review.

The gate is enforced on the built-in review preset only. Recovery
("Continue review" after a failed run) and explicit user-selected Circuits
stay permissive — both paths have already proven the source is observed in
another context.

A new **Review an agent that hasn't started yet** checkbox in the Start
Review dialog lets power users bypass the gate. The override is recorded
on the run's `context_json` (`source.review_allow_unobserved = "1"`) for
audit and support.

### Circuit watchdog fails fast on never-observed agents (#1791)

A Circuit step whose agent looks busy but has produced neither a session
identity nor a readable report is now ended after 15 minutes with an
explicit reason — "agent produced no session identity or report within
15 minutes — inspect the agent terminal" — instead of holding the run
for the full 120-minute active-wait budget. The watchdog still grants the
long budget once any progress is observed (including a session identity
captured later), approval gates keep their own behaviour, and a step that
pins its own `timeout_seconds` keeps that budget in full — the 15-minute
fast fail applies only to steps left on the default windows.

### Zombie agents are reaped instead of lingering as `running` (#1793)

An Autopilot/Circuit agent whose run timed out — or whose harness crashed,
exited, or never produced any observable evidence — could be left `running`
for hours with no session identity and no readable report. Nothing would ever
re-observe it, and later reviews and Circuit runs could still attach to it.

A periodic sweep now transitions such a node to a new terminal **Lost**
status (a red ⊘ *Lost* badge in the sidebar, mobile node list, and activity
header) and surfaces it through the standard agent-lifecycle event, so both
desktop and mobile update immediately. The rule is deliberately scoped to
**Circuit-piloted** nodes: a node you spawned by hand — including a
long-lived **Terminal** shell that never captures an identity — is never
reaped. A node that has captured a session identity, or produced a readable
assistant report, is left alone, and no node is inspected more than once per
observation window.

### Review circuits are gated on harness capability

The title-bar **Review** control on an Agent Node is now disabled when that
node's harness cannot report its own turn completion — it has neither an
attention hook nor a passive turn watcher. The same harnesses are no
longer selectable as the reviewer in the Start Review dialog or in
Settings → Providers; they stay visible in those pickers, greyed out
rather than hidden, so the limitation is discoverable rather than silent —
Settings → Providers labels them `(no review support)`, and the Start
Review dialog names the missing turn-completion signal.

Because Buildmesh cannot tell when such a harness has finished a turn, a
review Circuit started on one did not fail fast — it waited for a verdict
that could never arrive until its watchdog budget expired. The affected
harnesses today are **Freebuff** and **DeepSeek Harness**; **Terminal** was
already excluded as a plain shell. The backend enforces
the same gate at the circuit-trigger seam, so an unchecked call that
picks one of these harnesses as the reviewer is refused with a named
reason (for example, "Freebuff cannot be used as the reviewer provider: it
has no turn-completion signal") instead of minting a run that can never
reach a verdict. The gate also covers the inherit path: saving one of
these harnesses as the app-wide Reviewer provider is refused, and a
stale stored value refuses the run with Settings guidance.

Authored Circuits are unaffected: they carry their reviewer provider in
their graph, and a Blueprint author who picks an unsupported harness
explicitly is responsible for that choice.

### The Start Review dialog picks a reviewer with the shared Spawn Menu

Choosing a reviewer no longer uses a plain list. The Start Review dialog
renders the same harness-grouped Spawn Menu as every other spawn surface, so
picking a reviewer works the way spawning works everywhere else: harness rows
at the top, with each harness's saved Launch Configurations in its disclosure.
Picking a saved recipe applies that recipe's model and effort to the reviewer;
picking a bare harness row leaves model and effort to the harness's Mesh and
application defaults. Terminal stays excluded — it is not an agent.

## Fixes

### Codex continues when its Buildmesh callback is unavailable

Codex attention hooks no longer fail the agent turn when Buildmesh is shutting
down, temporarily unavailable, or has already archived the node. The callback
still updates Buildmesh lifecycle state when it reaches the app; a missed
callback cannot update that state.

### A live Muse agent is observable before Muse indexes it

A Muse Agent Node whose session was still running could stay invisible to
Buildmesh for its whole life. Muse publishes its session index asynchronously —
a live session has no index row until a later Muse process writes one — and
identity capture, the turn watcher, and the transcript reader all resolved
through that index. The node therefore had no session identity, no turn signal,
and no reportable transcript, so a Circuit or Review waiting on it failed after
15 minutes with "agent produced no session identity or report within 15
minutes". Buildmesh now also reads the per-session log Muse writes to disk,
which carries the same session id, workspace, and timestamp, and uses it
whenever the index has not caught up. Muse nodes in Circuits and Reviews become
observable as soon as their first turn is written.

### A review that yields mid-work no longer fails

A review Circuit whose reviewer yields while it is still working — a
background test run, or an intermediate progress note rather than its
findings — used to fail immediately: the `verdict` step read that progress
line as the reviewer's report and ended the run **failed** with **Review
needs attention**. The `verdict` step now confirms the reviewer has
actually finished its turn before it reads a report as the reviewer's
verdict, so the run waits for the reviewer's real findings instead of
judging the note. A reviewer that will not continue without you (a
permission prompt or a question) is still a real outcome, a finished
report is still judged exactly as before, and a reviewer that never
reports again is bounded by the step's existing wait deadline. A
transient classifier failure while the step waits is retried rather than
ending the run.

### Usage meters fall back to the last known reading on transient failures

A Usage meter whose live fetch fails transiently ÔÇö rate limited, transport
error, or the provider answering without usable quota (for example Muse
reporting no subscription usage) ÔÇö now shows the last reading that provider
reported instead of a bare error, whenever one was remembered in the last
seven days. Such rows carry a `Cached` badge in the row header: hovering it
shows when the reading was fetched, and the familiar "Last known value ┬À ÔÇª"
caption stays underneath. With nothing remembered the live error shows as
before, and an invalid API key still shows its re-entry prompt rather than
stale numbers.

### Clicking a file opens it without a terminal window

Clicking a file in the File Tree now opens it directly in the application your
system has registered for that file type - VS Code for the types it owns - and
no terminal window flashes on the way. The click used to launch the `code`
command-line launcher, which on Windows is a batch file and so opened a console
of its own before the editor appeared. The `code` launcher no longer needs to be
on your `PATH`, and this behaves the same on Windows, macOS, and Linux: a file
whose type is registered to a different editor now opens there instead.

## Providers & harnesses

### Grok attention hooks work with its HTTPS-only HTTP-hook policy

Grok's native HTTP hooks reject Buildmesh's local `http://localhost` callback
under SSRF protection. Buildmesh now provisions a platform-specific command
hook that forwards the event JSON to the loopback attention route with curl,
including the runtime hook token. On the next Grok spawn, existing generated
HTTP hooks are upgraded in place; user-authored hooks remain intact.

### Cline reports turn completion, so Autopilot and review circuits can use it (#1775)

Cline's CLI (3.0.62) resolves **file hooks** — executable files named exactly
after an event — from four fixed directories. Buildmesh provisions the
user-global `~/.cline/hooks` with `TaskComplete`, which Cline fires when a run
finishes with `status === "completed"`. A completed Cline turn now lands the
node in **Ready**, so Cline is eligible as an Autopilot provider and as a
review-circuit source or reviewer (it no longer shows `(no review support)`).

The hook file is additive and idempotent: a hook you wrote yourself is never
overwritten — Buildmesh fails provisioning and flags the node's signal health
rather than clobbering it — and the callback URL is expanded from the node's
own environment rather than baked in, so the file is never node-specific.

Cline's file-hook layer reports **only** a completed turn. It has no clean-exit
dispatch (a session ending normally emits nothing, so a node's exit is still
detected from the terminal closing, exactly as before) and no failure dispatch
Buildmesh installs, and Cline's default auto-approve launch raises no
permission or question prompt — so none of those signals is claimed. A run that
ends without completing produces no lifecycle event and is bounded by the usual
watchdog, the same as the other turn-completion-only harnesses.

### Cline sessions resume across restarts (#1774)

Cline 3.x self-assigns its session ids (`<epochms>_<5–6 base36>` — legacy `<13digit>_<5>` and current `session_<13digit>_<6>` shapes, for example
`1789757012702_7of3e`) and never prints them in the TUI, so the previous
release shipped Cline as an interactive-only harness: a fresh spawn landed on
the Spawn Menu but every Cline node kept `cli_session_id = NULL` and stayed
unresumable across restarts. v1.4.0 reads Cline's authoritative local SQLite
store (`~/.cline/data/db/sessions.db`) and splices `--id <id>` into the next
spawn's argv, so a Cline node that was running when Buildmesh quit (or crashed)
picks up the same conversation when it next opens.

Two paths share the same SQLite read:

- **Fresh-spawn capture** — a short retry loop (~9.3 s budget) on
  `services::cline_session::start_capture_poller` matches the spawn
  directory against the `sessions.cwd` column and picks the newest
  interactive row whose embedded epoch ms is inside the spawn window.
  One-shot prompt runs (no `-i`, positional prompt) carry
  `interactive = 0` and are filtered out by design.
- **Suspended-node recovery** — the startup resume sweep calls
  `find_historic_id_for_directory`, which re-reads the same store
  without the `not_before` clamp and applies the same one-candidate-in-window
  gate every other harness uses to avoid binding the wrong conversation
  when a user reopens the same directory twice.

The capture pipeline cancels when the node leaves the process registry, so
a Cline process killed before it flushed its `sessions` row cannot write a
zombie id. `CLINE_DATA_DIR` and `--data-dir <path>` overrides are honoured
by the resolver, matching `--help`'s precedence — Buildmesh never sets
them itself, but a Mesh that explicitly demands isolation keeps the
escape hatch.

See the [Cline harness capabilities](../learning/cline-harness-capabilities.md)
page for the full contract.

### Muse workspaces are trusted before the agent starts (#1706)

A Muse node ran with its workspace **untrusted**, so the guidance Muse was
supposed to load never arrived: the repository's `CLAUDE.md`/`AGENTS.md` rules,
its `.claude/skills` and `.agents/skills`, and any `muse init` scaffolding were
all silently skipped.

Muse gates those behind an explicit trust decision, and its only controls are
per-run: `--trust-workspace` trusts a workspace for one invocation and does not
save it, and `muse plugins install` accepts no trust flag at all — so no launch
flag could restore project context. Buildmesh now records the decision in Muse's
own persistent trust store, immediately before the spawn. The entry is merged,
never templated: other projects and any keys you added round-trip untouched,
re-spawning a workspace writes nothing, and anything Buildmesh cannot safely
write is reported as a failed provisioning step and left exactly as it was —
a file it cannot parse, or a workspace you already marked **untrusted** in
Muse, whose decision it will not overwrite.

Verified against the installed Muse 1.3.0: with the entry in place,
`muse skills list --workspace <dir>` lists the workspace's own skills with no
`project-skills-untrusted` diagnostic and no trust flag on the command line.
Approval policy and the OS sandbox are unchanged — `--yolo` is still never
baked in.

See the [Muse harness capabilities](../learning/muse-harness-capabilities.md)
page for the store format, key derivation, and evidence.

### Command palette tools grid decluttered

The command palette's first-open **Tools** grid and the inspector's **All
tools** menu no longer carry per-group scope notes. "Selected project" was
repeated on four of five group headings and the "App-wide" note duplicated
its own heading; the one genuine exception — Agent Changes follows the
focused agent — now appears in that tool's description ("Review what the
focused agent changed"). Group headings now carry only the group name,
leaving tool names and what each does as the sole remaining text.

## Interface

### The Spawn Menu drops the redundant "harness" tag

Every top-level row in the desktop Spawn Menu — and in the Regenerate
provider picker, which renders the same rows — is a harness now that saved
Launch Configurations live in each harness's `›` submenu, so the uppercase
**harness** tag on native rows is gone. The canvas empty state that
described the menu's pick as "the harness" now says "what to launch".

### Default provider settings use the shared Spawn Menu

The **Default provider** picker in Project Settings, and the **Default
provider**, **Reviewer provider**, and **Auto-naming** pickers in
Settings → Providers, now render the same harness-grouped Spawn Menu as
every other spawn surface. Each setting is a harness row with its saved
Launch Configurations in the `›` disclosure, and picking a configuration
saves that recipe as the default — it applies that recipe's model and effort
wherever the default is used. Previously these settings were flat lists
whose options differed from the menus you spawn from; creating or editing a
configuration is now available straight from the setting. A configuration
whose harness is hidden on this host is still shown by name when it is the
current selection.

### Per-harness overrides removed from Project Settings

Project Settings no longer offers the per-Mesh **Per-harness overrides**
list. A Mesh's model and effort now come from the application Harness
defaults (Settings → Harnesses) and from named Launch Configurations
selected per spawn; any previously stored per-Mesh overrides no longer
apply.


### Legacy Autopilot retirement and Circuit evidence (#1889, in progress)

Legacy automation is cancelled at startup and its owned processes are stopped;
nodes, worktrees and history remain available. The former controls show retained
settings read-only, with independent Circuit run capacity and a link to configure
Circuits manually. No settings or runs are automatically converted.

Circuit history separates report interpretation from lifecycle authority, labels
partial/unavailable reports, and shows current harness capabilities and evidence
deadlines. Spawn dispatch claims and attachment acknowledgements are durable;
unknown dispatches require evidence or a deliberate operator outcome. Acceptance
verification for the broader reliability change is still in progress. A Codex
completion rejected by a newer prompt or session leaves the same attempt
Unverified instead of leaving its recheck Running; rejected evidence is not
recorded.
