# Mobile Remote Access: Terminal Output Not Appearing

**Date:** 2026-05-10
**Status:** UNRESOLVED — actively debugging

## The Bug

When connecting from the mobile app to an agent node remotely:
- Mobile shows a green dot (WebSocket `onopen` fires)
- Terminal cursor is visible and blinks (xterm.js initialized)
- **No text appears** — the cursor is visible but PTY output is never displayed

## What Works

- Mobile can connect to the desktop app's HTTP server on port 1992
- Mobile shows green dot (WS connection is established from mobile's perspective)
- Desktop app receives the WS upgrade HTTP request and parses headers correctly
- HTTP API (`/api/nodes`) returns correct data
- PTY output is being generated by the agent (visible in desktop terminal)
- `send_pty_output` is called with correct data but `subscribers: 0` — no WS receiver

## Architecture

```
Mobile App (Chrome/Android)
    |
    | WebSocket ws://192.168.1.10:1992/ws/terminal/{nodeId}?token=xxx
    v
http_server.rs: handle_connection()
    - reads HTTP headers via BufStream
    - matches /ws/terminal/{nodeId} path
    - validates token
    - calls accept_async(stream)  <-- BLOCKING/HANGS
    - on success: spawns handle_ws_connection()
    |
    v
handle_ws_connection()
    - subscribes to KNOWN_NODES broadcast
    - requests terminal snapshot
    - spawns write_task: recv from broadcast, send to WS
```

## What We've Tried

### 1. Debug Instrumentation
Added `[DEBUG-pty]` logs throughout the WS path to trace execution:
- `WS path HIT` — confirms mobile's HTTP request reaches server correctly
- `headers before WS upgrade` — confirms all WS headers present and correct
- `calling accept_async` — confirms `accept_async` is reached
- `drain read N bytes` — always 0 bytes drained before `accept_async`
- `WS upgrade SUCCESS/FAILED` — `accept_async` always fails
- `handle_ws_connection ENTERED` — never logged (means Ok path never reached)

### 2. accept_async Timeout
Added 5-second timeout around `accept_async`. Result: always fails with:
- `"WebSocket protocol error: Handshake not finished"` (mobile connection)
- `"IO error: An existing connection was forcibly closed by the remote host. (os error 10054)` (desktop test)

### 3. Buffer Drain Before accept_async
Added explicit drain of BufStream before calling `accept_async` to handle buffered body data. Result: `drain read 0 bytes` — no buffered data found. Did not fix the issue.

### 4. Raw Socket Tests
- Desktop Python script sends raw WS upgrade request to `192.168.1.10:1992` — times out
- Desktop Python script sends raw WS upgrade request to `127.0.0.1:1992` — connection refused (no listener on IPv4 loopback for port 1992)

### 5. Mobile Behavior
- Mobile connects to `ws://192.168.1.10:1992/ws/terminal/392?token=...`
- Green dot appears quickly (WS `onopen` fires)
- But no text is ever rendered
- Mobile's `sendInput()` sends data, but server WS receive path never logs received data (server's WS read loop never executes)

### 6. Token Validation
- Token `65a46ee544d0875905631644d8cdc661` is valid
- Server confirms `WS path HIT: ... (token present: true)`

## Key Observations

1. **accept_async consistently fails** but mobile sees `onopen` — contradictory
2. **No `handle_ws_connection ENTERED` logs ever appear** — the success path of `accept_async` is never reached
3. **subscribers: 0** on every `send_pty_output` call — the broadcast channel has no active receivers because `subscribe_pty` is never called (since `handle_ws_connection` never runs)
4. **5-second timeout on accept_async** gives quick failure, confirming the server-side WS handshake doesn't complete
5. **Drain reads 0 bytes** — BufStream's buffer is empty after header reading
6. **Port 1992 only listens on 0.0.0.0 (all interfaces), not on 127.0.0.1** — desktop local WS connections go to `192.168.1.10` not `127.0.0.1`

## Hypotheses

### H1: tokio_tungstenite accept_async BufStream incompatibility
`accept_async` called on `tokio::io::BufStream<tokio::net::TcpStream>` may not work correctly because `BufStream` has internal buffering that interferes with `accept_async`'s own handshake reading. The function may consume bytes from the stream that `accept_async` expects to read, causing the handshake to see an incomplete/corrupted stream.

**Evidence:** `drain read 0 bytes` before `accept_async`, but `accept_async` still fails. The BufStream's internal state may still be affecting things.

**Fix attempt:** Call `accept_async` on the raw `TcpStream` instead of the `BufStream`. Requires refactoring to not use `BufStream` for WS paths.

### H2: Mobile's WebSocket completes via a different network path
The mobile's WS connection succeeds through a different network path (e.g., carrier NAT, VPN, different routing), while the desktop's server `accept_async` is dealing with a different TCP connection that fails. The green dot may represent a connection to a different service (not our Buildmesh HTTP server).

**Evidence:** Only the mobile reports success. All server-side tests fail.

**Fix attempt:** Not yet tested — would need mobile-side debugging (Chrome DevTools on phone).

### H3: Tauri/Tokio runtime blocking issue
`accept_async` is async but `handle_connection` runs in `tauri::async_runtime::spawn`. There may be a runtime context issue where `accept_async` doesn't properly suspend/await within the Tauri async context.

**Evidence:** The function blocks for 5+ seconds then returns an error.

**Fix attempt:** Not yet tested.
