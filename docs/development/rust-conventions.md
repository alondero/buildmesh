# Rust conventions and shared wire types

Status: current

## Database Pattern
Use `_inner` helper functions that accept `&Connection` so compound operations keep one connection and writer transactions never re-lock. Public read functions check out `read_conn()` from the eight-connection read-only pool; public mutations lock the dedicated `write_conn()`. SQLite WAL lets those readers run concurrently with the serialized writer. Async request paths use `try_read_conn()` so pool contention has a bounded wait and an error result. See `src-tauri/src/db/mod.rs`.

### Per-test database isolation (issue #2048)
Production opens exactly one database: `db::init` populates a process-global `OnceCell<Database>` once and later calls are a no-op. Under `cfg(test)` a thread may instead install its **own** database, and `db::get()` prefers it, so `read_conn()` / `write_conn()` / every `db::*` query in that test resolve to that test's rows and `cargo test` runs multi-threaded with no `--test-threads=1`. A test opts in with `let _db = db::test_support::isolated();` as its first statement and holds the guard for the whole body; `isolated()` is depth-counted, so a shared helper may call it again without replacing the caller's rows. This is the same shape `preferences::storage` already uses for its per-thread `APP_DATA_DIR` / `CACHE` (issue #1386), and `db::circuit_tests` already proved the per-test-database approach works (#1691). Variants and their reasons:

- `isolated_file()` — a real file, so commits pay the fsync an in-memory commit skips. For a test that *measures* commit cost, or that reopens the database by path (`PRAGMA database_list`) to simulate a crash restart. Files live in a per-process scratch directory the next run reclaims.
- `adopt(&handle)` — a `thread_local!` install does **not** follow the thread, so code a test hands to `std::thread::spawn` (or a multi-threaded tokio runtime) would resolve the global database instead: a "database not initialized" panic, or another test's rows. Pass a `handle.clone()` into the closure and `adopt` it there. A plain `#[tokio::test]` needs none of this — the default current-thread runtime polls the future on the test's own thread.

Two consequences worth knowing. Every isolated database owns a disjoint range of **agent-node ids** (`seed_unique_node_ids`), so a process-global keyed by an agent-node id (e.g. `circuit::evaluator::NODES`) cannot collide across parallel tests; other autoincrement ids (meshes, runs) still restart at 1 in every test, so reserve a process-unique id where a global is keyed by one of those. And the process **environment** is shared state too: a test that calls `set_var`, or that snapshots the whole environment, must hold `crate::env::ENV_LOCK`, or a parallel test's mutation leaks into it.

**Leave an agent-node id the number its database gave it.** The disjoint ranges above only make the id safe to key a process-global on while the fixture stays inside the range it was handed: renumbering a node into a private sequence (a `k * 1_000_000 + 1` counter, say) puts it back into the ranges the databases own, and the eleventh database's first id is `1_000_001` — the same value the first renumbering produces. Two parallel tests then share one evaluator key, and the loser's `unregister` drops the winner's PTY buffer, which surfaces as an intermittent assertion far from the collision (issue #2144). `db::test_support::installed_node_id_range()` returns the range the current thread's install owns, so a fixture can assert its node landed inside it.

**A test that *reads* an environment variable another test *writes* needs the lock too.** `ENV_LOCK` only excludes the threads that also take it, so a reader that skipped it observed whatever writer happened to run alongside it, and the assertion failed only under parallel libtest — `freebuff_credential_paths_includes_xdg_default` saw the sibling override test's tempdir as its XDG candidate (issue #2285). Hold `ENV_LOCK` across the read, and pin the variable with `with_env_vars(&[(name, value)], …)` so the assertion describes the value the test means rather than the caller's shell; `with_env_vars` restores through `catch_unwind`, so a failing assertion cannot leak the value into the rest of the suite.

**Never rewrite the process `PATH` in a test** (`with_env_vars` panics if asked to). On Windows every spawn of `git`, `node` or `powershell.exe` resolves the program through the process-wide `PATH`, so a test that swaps it, even briefly and even under `ENV_LOCK`, makes unrelated tests fail with `program not found` (issue #2109). Pass the search path to the code under test instead, as `session_naming::ClaudeSearch` does.

**Fixture directories next to a `TestDir`** (a bare origin, a clone) come from `TestDir::sibling(suffix)`, which clears a stale directory and removes it on drop. Hand-built siblings leaked, and Windows recycles process ids, so a later run found the earlier run's bare repository and every push to it was rejected. Sweep for stragglers: a fixture still building `%TEMP%\buildmesh_*_<pid>_<n>` by hand has the same leak, whether or not it has failed yet — the two bare repos in `agent::spawn::provision_tests` had accumulated over 20,000 such directories by the time #2123 moved them onto the seam. Clearing the directory yourself before use hides the leak but not the unbounded accumulation.

**A `TestDir` claims its directory; it does not adopt one.** `TestDir::new` names the directory with a per-process wall-clock token alongside the pid and counter, then creates it with an exclusive `create_dir`, disambiguating (`_1`, `_2`, …) when a name is already taken. Two mechanisms, because they answer different questions: the token makes the name unique to this process instance, and the exclusive create is what keeps it safe — it steps *around* a survivor instead of deleting whatever an earlier run left behind. It used to `remove_dir_all` and then `create_dir_all`, which is adoption: a recycled pid plus counter meant a run deleted and then inherited the previous run's bare origin, so the fixture's very first push was rejected `HEAD -> main (fetch first)` before any code under test had run (issue #1992). `git init --bare` and `create_dir_all` are the two calls that made this silent — both leave existing contents in place, so a stale remote looks like a working one until the push fails. `env::test_helpers::claim_dir_steps_around_a_directory_an_earlier_run_left` pins the claim; `git::sync::fetch_origin_tests::fetch_origin_fixture_starts_from_independent_history_over_a_leaked_origin` seeds a leaked origin at the exact path the fixture will take and pins the resulting independent history and cleanup.

**Waits and locks with a wall-clock budget** (a lock-wait timeout, a "finishes within N ms" assertion) are the other source of load-dependent failures. Inject the budget (`prepare_waiting(path, wait)`) or assert the mechanism (a flag that records the watchdog firing), not a stopwatch; see #2049. A test that spawns a real process, or waits on an OS handle, needs a budget a *loaded* machine can meet: four Windows tests failed only while other worktrees ran `cargo test` (issue #2173). Poll with a sleep, not `yield_now` — a busy spin steals the CPU the wait is competing for.

**Probing the Windows error before matching on it.** Which error a lock contention produces is an empirical question, and guessing it ships the wrong predicate. Three measured facts on Windows 11:

- A `create_new` against a file another handle holds with `share_mode(0)` reports `ERROR_FILE_EXISTS` (os error 80) — *not* an access-denied or sharing error. Matching only `AlreadyExists` is therefore not "the contention case".
- The same `create_new` reports os error 5 when the *directory* refuses the write — a deny ACE, a scanner, a filesystem filter. That is indistinguishable from a busy lock by probing the lock file, so `acquire_transaction` retries it inside its existing budget rather than failing the launch (issue #2173). A write-denying ACE (`icacls <dir> /deny <user>:(W)`) reproduces it deterministically, and a test can assert that precondition so it cannot pass vacuously.
- An open handle *inside* a directory blocks the directory's rename-into-staging with os error 5, and the delete that follows is never reached. So `remove_worktree_dir_with_retry`'s retry budget is the entire close-node window, and widening that budget is the fix — there is no second stage to retry.

**A fixture that reopens a hard-killed child's database gets `SQLITE_IOERR_TRUNCATE`, and it names a refused file resize rather than a failed read.** SQLite's Windows VFS raises extended code 1546 (`SqliteFailure(SystemIoFailure, 1546)`, `"disk I/O error"`) from a failed `SetEndOfFile`; the trigger is `winLockSharedMemory`, which **truncates the `-shm` WAL-index file to zero** when a process is the first to map it. A child killed by `abort()` — and any real-time scanner that opened the files it had just written — can still be holding that file, so statements on the reopened database fail with it until the OS lets go. That is machine load, not a damaged database: `services::legacy_retirement::retirement_crash_tests` failed 18 of 24 concurrent rounds with this error, in three separate seams, and passed alone (issue #2375). Reopen inside a bounded poll that runs a statement mapping the WAL-index (`PRAGMA schema_version`) before the caller's own work — the same discipline that fixture already uses to wait for the OS to finish killing a contained process — and retry only `ErrorCode::SystemIoFailure`, so a corrupt or missing database still fails at the caller's own `.expect`.

## Typed db errors

`db` reports failures as `DbError` (`src-tauri/src/db/error.rs`), not as a hand-written `String`. The layer's domain modules re-export it; callers reach it as `crate::db::DbError`.

- **Build the kind, don't compose prose.** `DbError::not_found` for a row named by id or identity that is gone, `DbError::conflict` for a write that lost a race or contradicts current state (revision moved, run went terminal mid-commit, agent already owned), `DbError::invalid` for a well-formed request that cannot be carried out as asked. A caller then branches with `matches!` instead of `err.contains("… no longer exists")`, which is what broke in #2446.
- **Let `?` do the rest.** `From` is implemented for `rusqlite::Error` and `serde_json::Error`, so a bare `?` yields `Sql` / `Json` — no `.map_err(|e| e.to_string())`, which was pure noise that also hid the kind. The db pilot deleted 163 of those closures in nine files. `From<String>` carries a message some *other* layer rendered first (`circuit::context`, `circuit::model`, `preferences`, and the step-recovery refusal funnel); those producers get their own enums in their own slices.
- **The rendering is frozen.** Every variant renders byte-identically to the `String` it replaced. Tauri serializes a command error as a `String`, so that text *is* what the user reads — it is product copy, not an implementation detail. `From<DbError> for String` renders through `Display`, which is what lets a `Result<_, String>` command keep working unchanged. The `tests` module in `error.rs` copies the shipped phrasings — including near-duplicates that differ only in punctuation — so a refactor cannot smuggle a reword. Changing a message is a user-visible change with its own slice. (Spot-checking these strings across `src/` and `tests/` found no TypeScript that branches on them: the consumers are the user and the Rust tests in `db/`. Don't assume a frontend contract here that isn't there — and re-check before assuming the copy is yours to reword.)
- **A variant nothing constructs is a paper tiger.** `db/mod.rs`'s reader-pool timeout and `db/migrations.rs`'s schema repair are still a `rusqlite::Error::InvalidQuery`; they are not `DbError` variants yet because those modules are `SqlResult` and promoting the sentinel would change what the frontend renders today. Add the variant in the slice that owns the condition.
- **`SqlResult` is still the right type** for a function that only returns a SQLite error (`crate::db::SqlResult`). Reaching for `DbError` there would borrow the payload type `String` into an unrelated error enum for no gain.

## Process-group signals

Signal a process group with `process_util::kill_process_group`. It calls `kill(2)` with the whole negative id and refuses `0` and `-1`.

Do not shell out to procps `kill` with a negative id (`kill -KILL -<pid>` without `--`). On Ubuntu 24.04 that binary keeps only the first digit. A pid whose first digit is 1 becomes `-1`, and `kill(-1, SIGKILL)` signals every process the user can reach. On a GitHub-hosted runner that includes the runner agent, so the job ends with no step conclusion and no log (issue #2103). The `services` shard started losing runners once tests ran multi-threaded, because the cancelled verification's pid then landed in a leading-1 range. `scripts/check-process-spawn-discipline.mjs` rejects `command_no_window("kill")`.

## Command Threading (blocking work must not touch the async worker pool)
A `#[command]` on an `async fn` **and** `#[command(async)]` on a sync `fn` both run on Tauri's bounded tokio worker pool (≈ CPU cores). Only a plain sync `#[command] fn` runs off it. So a command that does a **blocking network call** (`reqwest::blocking`, `git fetch`/`git pull` shell-out), a **SQLite transaction** (`db::*` / `db::write_conn`), a **disk read/write** (`std::fs::*`, `preferences::load`/`save`), or a slow libgit2 walk on the async runtime **parks a worker for the whole duration**; enough of them stuck at once starves the pool and every other async command (agent keystrokes, WebSocket streaming, probes) stops being polled while the UI stays alive — the class of bug behind the overnight-freeze (issue #762 / #1380: see the `run_blocking` wrappers in `commands/pr.rs`, `commands/github.rs`, `commands/agent_node.rs`, `commands/preferences.rs`). Convention: give each such command a **plain-sync core (`*_blocking`)** and a thin `#[command] async fn` wrapper that offloads it via `crate::commands::run_blocking(label, || core(..))` (which threads it through `tauri::async_runtime::spawn_blocking`). Fast in-memory lookups may stay as a plain sync `#[command] fn` (the circuit CRUD commands do this). The mobile HTTP routes (`http/routes/*`) are **not** a separate pool — `http/mod.rs` spawns each connection on the same `tauri::async_runtime`, so a route that calls a `*_blocking` core directly still parks a worker; routes are `async fn`, so they must **`.await` the async command wrapper** (e.g. `get_repo_issues(id).await`) or `run_blocking` themselves, letting it offload. Gated by `tests/unit/async-command-blocking.test.ts` (issue #1380); per-line opt-out: `// allow-blocking-on-async: <reason>`. Only reach for a `*_blocking` core from a genuinely synchronous context (e.g. `check_gh_auth_cached`, itself run inside `run_blocking`). Also give any blocking network client a finite `.timeout(..)` (`GitHubClient` uses `build_http_client`) so a half-open connection can't hang forever.

## Dev-only IPC commands (keeping them off the release window)
A `#[command]` that exists only for tests or crash diagnosis is registered behind `#[cfg(any(debug_assertions, feature = "dev-tools"))]`, never unconditionally. `create_test_mesh` writes a Mesh row into the user's real database and `debug_list_agents` / `debug_crash_snapshot` expose process-registry state; a shipped build must answer "command not found" for all three (issue #2153). `debug_assertions` covers `cargo build` and `tauri dev`; the dev profile is built by `tauri build` (release mode, see `scripts/run-dev.ps1`), so `npm run tauri:build:dev` passes `--features dev-tools`. The feature is declared default-off, and the release build entry points — `npm run tauri build` (which `.github/workflows/build.yml` runs), `scripts/run.ps1` and `scripts/run.sh` — pass no feature flag.

Put the same `cfg` on the command function itself, so the compiler keeps the two halves in step: gating only the handler entry leaves a dead `#[command]` (a release-mode dead-code warning), and gating only the function fails to compile.

The same rule reaches one level down. A plain function whose only callers are the dev-gated modules (`commands/test.rs`, `services/test_fixtures.rs`) or `#[cfg(test)]` code carries a matching `cfg`, so a release build compiles neither the callers nor the function and reports nothing. `db::delete_mesh` and `db::archive_agent_node` are reached from the test-bridge handlers and from unit tests; `services::mesh::create_test` from the dev-gated `create_test_mesh` command and the fixtures; `db::circuit::recovery::continue_failed_review` from the fixtures; and the recovery-ledger helpers from the fixtures and unit tests. Gating them keeps test-only SQL and temp-directory writes out of a shipped binary and turns what would be a dead-code warning into an explicit decision. Include `test` in the list only when a `#[cfg(test)]` consumer needs the item: `cargo test --release --lib http::fuzz` is a supported command and that build has `debug_assertions` off. `cargo test --release --lib --no-run` is the cheap proof that every such consumer still resolves — a plain `cargo check --release` never compiles the `cfg(test)` half, so it cannot catch a missing `test` in the list. No CI job runs that compile (the Rust test binaries are built with the default profile), so it stays a local check rather than a gate. An enum variant is a consumer like any other — gate a variant that is only constructed inside a `#[cfg]` block, and gate its `match` arms with it, or a release build warns that the variant is never constructed. The proof is `cargo build --release`: a `dev-tools` or `debug_assertions` build cannot see this, because it compiles the callers.

The HTTP test bridge (`src-tauri/src/commands/test.rs`) is behind the same `cfg`. `run_profile_startup` calls `start_test_server` only in debug and `dev-tools` builds, and the listener still stays closed unless the process sets `BUILDMESH_TEST_BRIDGE=1` and `BUILDMESH_TEST_BRIDGE_TOKEN` (at least 32 non-whitespace characters). Launchers pass that token in the environment (`scripts/run-dev.ps1 -TestBridge`, `scripts/run-dev.sh --test-bridge`, and the e2e and smoke harnesses). The bridge does not serve a token endpoint. `tests/unit/ipc-contract.test.ts` checks that cfg text in `lib.rs`, `commands/mod.rs`, and `services/mod.rs`. That is a source check. This repository does not inspect a release binary to prove the listener is absent. The release entry points (`npm run tauri build`, which `.github/workflows/build.yml` runs) do not pass `dev-tools`, so those builds do not compile the call. Fixture tools that need the bridge (`invokeViaHttp`, `scripts/ui-shot.mjs`, the Android live check, the Codex recovery smoke) send `Authorization: Bearer`.

Debug and `dev-tools` builds read `BUILDMESH_PROFILE_DIR` before `app_data_dir()`. The value is the profile directory itself (it contains `buildmesh.db`, `logs/buildmesh.log`, `logs/panic_early.log`, and `tls/`), and it must be absolute. Certificate reads go through `preferences::app_data_dir()`, which startup sets from that resolved directory. A set but empty or relative value fails startup instead of falling through to the real profile. Release builds do not compile that read, so the variable cannot move a shipped profile. On Windows, `APPDATA` does not move the profile: Tauri resolves the roaming folder through the shell known-folder API. The e2e launcher and the Codex recovery smoke set `BUILDMESH_PROFILE_DIR` to a scratch directory. The e2e hub guard reads `instance-owner.pid` in the real stable profile. The hub does not bind port 1991.

A dev-only command must not have a wrapper in `src/`, because `src/lib/tauri.ts` and the stores ship with the app and the wrapper would only fail at runtime. `tests/unit/ipc-contract.test.ts` enforces both halves: the exact set of dev-gated handler entries, and no `invoke('…')` in `src/` targeting one.

## Dead code policy

`#[allow(dead_code)]` and `#[allow(unused_imports)]` are decisions, not plumbing. Each one in `src-tauri/src` asserts that an item is still worth carrying, and a bare attribute makes that claim unreadable and unverifiable. Both lints are the compiler telling you the truth about a build you are not looking at: `dead_code` is evaluated per configuration, so an allow justified by a test-only caller is a claim about the **release** binary that nobody checked, and an `unused_imports` allow on a re-export slab hides a name that no call site has used since the slab was written. Untracked dead code is worse than none: it gets edited, "maintained", and shipped, it rots test-coverage metrics, and it makes the `grep` archaeology this repo relies on (issue numbers in comments) lie about what the program does.

Resolve each one in this order (issue #2450 purged the backlog):

1. **Genuinely dead** — no reference anywhere, tests included. Delete the item and everything only it reaches. Confirm with `cargo check --all-targets` after the deletion.
2. **Test-only** — put the item (or the `use` that feeds it) behind `#[cfg(test)]`, matching the dev-only convention above. This is the fix for the `#[allow(dead_code)] // Used by unit tests in this module only` shape: an item the release profile compiles but no release path calls is code the user ships with no caller.
3. **Module-root re-export that nothing imports** — delete the name from the `pub use` slab instead of silencing the slab. `mod preferences`, `mod http` and `mod db` are private to the crate, so a `pub use` in them has crate-internal reachability and *does* warn when unused; the allow was covering the whole list, including the entries no call site wanted.
4. **A real false positive on a live item** — keep the allow, with an inline justification naming what breaks without it and the tracked issue that owns the follow-up. The live cases that survive today are an RAII-hold field whose value is only dropped (`instance_guard::PlatformGuard`), a setter whose production consumer is the *poll* rather than the write (`GitHubClient::cancel`), two `TS` payloads the frontend imports although Rust never constructs them, payload/envelope types production fills but only tests read, and one enum variant that a non-Windows-only arm constructs.

An allow that carries neither a reason nor an issue number does not survive review. `tests/unit/rust-dead-code-policy.test.ts` enforces exactly that: every `allow(dead_code)` / `allow(unused_imports)` attribute in `src-tauri/src` must sit next to a comment citing an issue, and `allow(unused_imports)` must be absent entirely. Note that `dead_code` fires per configuration — check the *release* shape too (`cargo build --release`, or a `cfg_attr(not(debug_assertions))` item), because a default-profile `cargo check` compiles the callers that the release binary omits.

### Test-only items live in a `*_tests` module, at the bottom of the file

An item with no production caller belongs behind `#[cfg(test)]` — but put it in a sibling module declared with `#[cfg(test)] mod <name>_tests;`, and declare that module **after** the production code, not among it. Two reasons, both enforced:

- **Source-scanning guards stay simple.** `agent::output::process_lifecycle_does_not_unregister_node_output_subscription` walks `src/` looking for call sites a release build compiles, and takes a file's production text as everything before its first `#[cfg(test)]` attribute line. That shortcut is only sound while gated items come last; `sink_call_sites_are_not_followed_by_a_gated_item` asserts it on every file the walk visits. A gated function dropped mid-file would otherwise hide every call site after it. The alternative — a hand-rolled brace/string tokenizer to resolve gates structurally — is a Rust parser written in the wrong place, and it broke twice before it was right.
- **The reader can tell production from test by position.** A file whose first 900 lines are `#[cfg(test)]` tells you nothing about what ships.

`#[cfg(test)]` inside a production module is still fine for a single test helper that is genuinely co-located with what it tests; the rule is about the long-lived test support modules.

## Injectable Caches (avoid process-global statics)

The frontend Git-query caches share one `GIT_CHANGED` bus in
`src/lib/pathInvalidatedCache.ts`. A dispatch invalidates each client/key once
before notifying its consumers, so their refreshes share the same request.
Events during a slow request defer one follow-up refresh rather than repeatedly
superseding it; the running request can publish while edits continue.
Only the currently registered pending promise may commit a value/error or clear
request ownership; superseded callers adopt the current request/value. Trailing
refreshes retain subscription objects and unsubscribe removes them, cancelling
the timer when no consumers remain. The native file-watcher coalescer uses a
single-slot non-blocking wake channel: signals contain no file data and one wake
is enough to request the latest state. See the
[performance review](../archive/2026-10/performance-audit-2026-10.md) for evidence and
remaining retention/coverage work.

Process-global `static OnceCell<Mutex<_>>` caches with test-only `#[cfg(test)]` forks (or per-test `GH_AUTH_CACHE_TEST_LOCK`) are flaky — `cargo test -- --test-threads=8` still racy via snapshot-delta tricks and they hide production synchronization bugs (see #1482 preferences, #1483 gh-auth). Prefer an injectable struct (`services::gh_auth_cache::GhAuthCache` — single `Arc<Inner>` with `slot: Mutex<(Instant,bool)>` + `misses: AtomicU64` + injectable `now`/`auth` closures, `Mutex` held across `auth_fn` to coalesce concurrent misses to one HTTPS call). Wire one instance via `tauri::Builder::manage(GhAuthCache::new())` and take `tauri::State<GhAuthCache>` in the `#[command] async fn`; the `*_blocking` core takes `&GhAuthCache` and calls `cache.check()` directly (runs on `spawn_blocking`, so blocking there is the intended coalescing). Tests use `GhAuthCache::for_test_with_auth()` per `#[test]` (isolated counter, stubbed network, controllable `now` via `for_test_with_clock_and_auth` or `expire_for_test()`). See `src-tauri/src/services/gh_auth_cache.rs` and `src-tauri/src/lib.rs:manage`.

## Rust unit tests live in sibling `*_tests.rs` files
A module's unit tests are a sibling `*_tests.rs` beside it, attached with `#[cfg(test)] #[path = "…_tests.rs"] mod tests;` instead of an inline `#[cfg(test)] mod tests { … }` (#2451 moved the fourteen largest inline blocks — `db/circuit/evidence.rs` alone carried ~4,800 test lines). **The module keeps the name `tests`, and that is load-bearing**, because a test's identity is its full path `<owner>::tests::<name>`: the `rust-tests` shard matrix in `.github/workflows/verify.yml` selects by *substring match* on that path, `scripts/harness-corpus.json` pins whole test names as gate commands (`agent::spawn_environment::tests::format_powershell_command`), and `scripts/known-flakes.json` keys flakes by full name. Some `#[path]` modules do take their name from the file instead (`commands::prune::prune_tests`), which is fine — but a *rename* moves every test path at once, so the shard filters, the corpus commands and the flake keys have to move with it or the CI filter silently runs zero tests.

The file name is not the module path, and no path walk can derive it: `db/circuit/evidence_tests.rs` belongs to `db::circuit::evidence::tests`, not `db::circuit::evidence_tests`. So every `#[path = "…"]` module needs an entry in `RUST_PATH_INCLUDES` (`scripts/harness-check.mjs`), which `pathIncludeDrift` holds in both directions — a missing entry maps the file to a filter that matches no test, and a stale entry masks a file that stopped being included. That check regexes raw source **including comments**, so writing the attribute literally in a comment anywhere under `src-tauri/src/` registers a phantom `<dir>/…` file and turns the gate red; write `` `#[path]` `` instead. The fourteen headers #2451 added each tripped this, and `test:agent` caught all of them at once because `pathIncludeDrift` collapses duplicates per directory. Two more rules, each paid for by a review round:

- **Move the body verbatim, then format.** Unindenting by hand while moving edits the contents of any raw or multi-line string literal in the tests, and nothing notices. Format afterwards with `node scripts/rustfmt-touched.mjs <file>…`, which normalises indentation without touching literals. Finding the block's end needs the same care: a line that merely *starts* with `}` does not prove it closed the module (items may sit at column 0 inside a `mod` body), and a `\` line continuation inside a string literal silently shifts every line index after it.
- **A production module carries no `#[cfg(test)]` items.** A test-only helper belongs in the test file — `evidence.rs` held `evidence_view_inner` (which wraps `evidence_view_unresolved` in one call, for tests that keep their connection across both halves) in shipped source until #2451. `grep -n '#\[cfg(test)\]' <file>` on a module whose tests have moved should return exactly the `mod tests;` declaration and nothing else; a few small test-gated helpers may predate the split and stay.

A source-shape guard that scans "everything above the inline `mod tests`" has to survive the tests leaving. Degrade it to scanning the whole file — `map_or(source, …)` — instead of asserting the marker is still there. `codex.rs::tests::no_codex_read_probe_spawns_without_a_timeout` used to `split_once("#[cfg(test)]\nmod tests {").expect("codex.rs must keep its #[cfg(test)] mod tests block")`, which made the file's own layout a load-bearing fixture: the split became the assertion's premise rather than its subject.

## Pattern Guards (lint-style unit tests)
The repo runs a small fleet of "pattern guard" unit tests that walk source files and fail on text patterns known to ship a silent regression. They live under `tests/unit/` and run in the standard `npm test` / `scripts\check.ps1 unit` loop:

- `tests/unit/ipc-contract.test.ts` (issue #163) — every `invoke('name', …)` literal in `src/` must be registered in `tauri::generate_handler![…]` in `src-tauri/src/lib.rs`. Companion: each `#[command]` MUST be added to that handler list too (the symmetric trap). It also pins the dev-gated entries and fails if `src/` still wraps one (see *Dev-only IPC commands*).
- `tests/unit/webapi-on-this.test.ts` (issue #156) — forbids `this.x = <WebAPI>` (e.g. `this.scheduler = requestAnimationFrame`). In Chromium/WebView2 the WebIDL receiver binding throws "Illegal invocation" when the API is invoked through an object property. Fix: wrap the API in an arrow function (`this.scheduler = (cb) => requestAnimationFrame(cb)`) or `.bind(window)`. Per-line opt-out: `// allow-webapi-on-this: <reason>`, mirroring the `// allow-dispose` / `// allow-wsl-path` convention enforced by `.claude/hooks/guard-antipatterns.mjs`. See memory `buildmesh-webapi-receiver-binding` for the full receiver-binding story.
- `tests/unit/async-command-blocking.test.ts` (issue #1380) — an async `#[command]` in `src-tauri/src/commands/` must not call `db::*`, `std::fs::*`, or `preferences::load`/`save` except inside `run_blocking` / `spawn_blocking`. Per-line opt-out: `// allow-blocking-on-async: <reason>`.
- `tests/unit/radii-audit.test.ts` (issue #733) — no bare `rounded` (or bare directional `rounded-r` / `-l` / `-t` / `-b` / …) may survive anywhere in `src/components/` unless it is the one intentional chip pinned in `ALLOWED_BARE_ROUNDED`. Use a size-suffixed variant (`rounded-md` / `-sm` / `-lg` / `-full` / …) or pin the line with an `allow-bare-rounded` marker. The radius conventions themselves live in `DESIGN.md`; this guard only enforces them.
- `tests/agent-infra/git2-ownership.test.mjs` (issue #2194) — production Rust outside `src-tauri/src/git/` must not mention `git2::`, except the allowlist named in that test and in the module map's seam-debt list. It runs from `npm run test:docs`. The parser cases live in `tests/unit/git2-ownership.test.ts`. A Vitest walk of every Rust file would make a Rust-only edit rerun the frontend suite. A `#[cfg(test)]` item, a `*_tests.rs` file, or a `tests.rs` file is a fixture. Shrinking the allowlist is the work. Growing it is a review decision.
- `tests/unit/guard-antipatterns.test.ts` — unit-tests the pure helpers exported by `.claude/hooks/guard-antipatterns.mjs` (`checkContentViolations`, `checkWorktreeEscape`).

CI additionally runs a Rust-side text-pattern guard in `.github/workflows/build.yml` (no `std::process::Command::new("git")` and no inline `.creation_flags(` outside `process_util.rs`, per issue #665 / #690). The opt-out comment `// allow-inline-process-spawn: <reason>` is honored only by that CI step.

When writing a new pattern guard, mirror `ipc-contract.test.ts`: walk the tree, strip comments, apply a regex, report `file:line` violations in the failure message, and synthetic-test each input case so the regex is provably not a placebo. Test the *opt-out* path (escape hatch honored) and the *negative* path (hatch on a wrong line is NOT honored) — same pattern as the `// allow-dispose` tests in `guard-antipatterns.test.ts`.

## Shared Rust↔TS Types (wire-shape source of truth)
Wire types that cross the Tauri `invoke` boundary **or** the mobile HTTP server are generated from Rust with [`ts-rs`](https://github.com/Aleph-Alpha/ts-rs), not hand-declared in TS. The Rust struct is the single source of truth (issue #359).

- **Producing a type:** add `TS` to the derive list and `#[ts(export, export_to = "Name.ts")]` to the struct/enum (e.g. `models::Mesh`, `models::AgentNode`, the `EnvType`/`Provider`/`SessionStatus` enums, `commands::pr::GitHubIssue`, `commands::git::GitStatus`, `services::session_discovery::DiscoveredSession`).
- **Generation:** `cargo test` (run in `src-tauri/`) runs ts-rs's auto-generated `export_bindings_*` tests, which write `.ts` files to `src/types/generated/`. The dir is set by `TS_RS_EXPORT_DIR` in `src-tauri/.cargo/config.toml`. **Generated files are committed** and must never be hand-edited (they carry a "Do not edit" banner).
- **Consuming a type:** import from `src/types/generated/`. Stores and `src/lib/tauri.ts` / `src/mobile/api.ts` re-export the generated type under the name call sites already use.
- **`i64`/`u64`/`usize` → `#[ts(as = "i32")]`** (and `Option<i64>` → `#[ts(as = "Option<i32>")]`). ts-rs defaults 64-bit ints to `bigint`, but serde_json sends them as JS numbers; the annotation makes the generated type say `number`. Forgetting it produces `bigint`, which fails the TS build — drift caught, not shipped.
- **`Vec<i64>` on the wire — use `Vec<i32>`.** There's no precedent in this codebase for a `Vec<i64>` field on a ts-rs-exported struct; ts-rs generates `Array<bigint>` from `Vec<i64>` directly, breaking the JSON-over-IPC contract. When a ts-rs-exported struct needs a list of integer IDs (e.g. issue #481's "blocked-by" list), use `Vec<i32>` on the wire struct — it matches the per-element `#[ts(as = "i32")]` cast convention and ts-rs emits `Array<number>` natively. Keep the internal `services::*` struct as `Vec<i64>` (GitHub's native integer width) and downcast in the command mapper with `.map(|n| n as i32).collect()`. `#[serde(default)]` on a `Vec<T>` field deserialises a missing key to `vec![]`, keeping the wire additive across rolling deploys — the wire changes without a coordinated frontend cutover.
- **serde attributes are honoured** (ts-rs `serde-compat`, on by default): `#[serde(rename_all = "snake_case")]` on `SessionStatus` makes the union `"awaiting_input"`, matching the DB and frontend. (A `rename_all = "lowercase"` here silently emitted `"awaitinginput"` — the exact drift class #359 closes.)
- **CI gate:** `.github/workflows/build.yml` runs `cargo test` then `git diff --exit-code src/types/generated`. A Rust struct change that isn't reflected in committed bindings fails the build.
- **Per-harness capability *values* (ADR-0037):** ts-rs generates the `HarnessCapabilities` *type*, not the per-adapter table. The total catalog is `builtin_harness_catalog()` in `src-tauri/src/agent/harness_catalog.rs` — every `Provider` variant, `adapter().capabilities()`, plus the Inspector/docs label, independent of detection. `cargo test` writes `src/types/generated/HarnessCapabilitiesTable.ts` (and `.json` for the docs gates). The Circuits Inspector and README/docs coverage consume that artifact. A hand-written TypeScript mirror of those values is a defect; `list_providers` is not a substitute because it only returns detected/configured rows. The profile id `claude` is an alias of the `anthropic` adapter (`HARNESS_PROFILE_ALIASES`), not a silent default.
- **Probe prompt preview contract:** `agent::spawn::intent` exports `src/types/generated/ProbeSpawnPromptExamples.json` during `cargo test`, using the production issue/PR renderers and template constants. The settings tests compare rendered previews, token buttons, and sample values against this fixture. Regenerate it when changing spawn templates, substitutions, or the shared review policy; CI's generated-artifact drift gate covers it.
- **UI presentation is not a second wire type.** `src/lib/status.ts` `STATUS_CONFIG` maps a generated session status to a glyph, label, and colour. `DiffHunk`, `DiffLine`, `DiffResult`, `FileNode`, `OpenPr`, and `GitBranchStatus` are generated; `src/lib/tauri.ts` imports them from `src/types/generated/`. Do not hand-declare those shapes again.
