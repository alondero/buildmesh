# Autopilot circuits

Status: current

## Autopilot Circuits (spec #1205, walking skeleton #1206)

The application automation runtime is a composable trigger-action graph. A **Circuit** is a blueprint DAG (`circuit::model::CircuitGraph`, serialised as the `graph_json` TEXT column — no per-node-kind migrations, the AST evolves inside the JSON); a **Circuit Run** is one execution (`autopilot_circuit_runs`); a **Circuit Step** is per-circuit-node state within a run (`autopilot_circuit_run_steps`, schema v34). "Node" is overloaded everywhere: *circuit node* = graph vertex, *agent node* = mesh session.

- **Pure core, thin impure seam:** `stepper::advance(run, event) -> Transition {step_writes, effects}` never touches SQLite/PTY/clocks — every impure fact arrives as an event (`Tick(Capacity)`, `AgentFinished`, `AgentReady`, `AgentLost`). The seam is `services::circuit_worker`: a dedicated OS thread (2s fast tick + condvar wake for Trigger Now) that observes live state → steps → commits atomically via `db::commit_circuit_advance` (one transaction for run-state + all step upserts; `UNIQUE(run_id, node_id)` backs the upsert) → executes effects. GitHub effects live in `circuit_worker/github.rs`; spawn overrides in `circuit_worker/spawn.rs` — a new effect kind should not enlarge the loop.
- **Single vocabulary owner (issue #1660):** `circuit::vocabulary` owns `RunState` / `StepStatus` (`Queued` stores as `pending_slot`) and the terminal predicates. Persistence, the worker, and the UI import those tokens (generated `RunState.ts` / `StepStatus.ts` + `circuitVocabulary.ts`). Do not re-spell `pending_slot` or terminal sets at call sites.
- **Single capacity policy (issue #1660, ADR-0028 limits minus the step budget ADR-0042 retired):** `circuit::capacity` owns admission arithmetic, Tick snapshots, and `CapacityBind`. The worker observes counts then calls `may_admit` / `tick_capacity`; the Probe explains a parked run with `pendingAdmissionDetail` (run admission) and a parked step with `queuedReason` (a constant agent-lease explanation, since only an agent spawn can park). Do not re-derive slot math in the UI or worker.
- **Trigger dedupe lives in the schema**: `UNIQUE(circuit_id, trigger_identity)` + `INSERT OR IGNORE` replays the existing run id. Circuit-scoped, so two circuits may react to the same source independently.
- **Concurrency:** the circuit and legacy Autopilot policies are separate (issue #1467, ADR-0028):
  1. **`meshes.autopilot_concurrency_limit`** is the legacy Autopilot agent-node cap. The circuit worker does not read it; changing the legacy "Max concurrent autopilot nodes" setting must not change circuit-run admission or circuit fan-out.
  2. **`meshes.circuit_run_capacity`** (schema v36) bounds the **admitted circuit runs** on a mesh (`db::count_active_circuit_runs`, count = `running + paused`). One slot per admitted run regardless of fan-out agent count. Default `2`; range `1..=8` validated at the IPC boundary (`update_mesh_circuit_run_capacity`). The worker reads this column in `run_pass` to gate the `pending → running` flip (`may_admit_run`); a `pending` run stays in DB `state = 'pending'` (NOT a step status) until a slot frees.
  3. **There is no per-circuit step budget (ADR-0042).** Within an admitted run, `stepper::schedule_ready` gates steps only by DAG eligibility plus the agent lease below: edges serialize, branches parallelize, and `cascade_after_completion` starts every newly eligible non-agent successor at once. `autopilot_circuits.concurrency_limit` is a retired column kept so an older build can still open the database; nothing reads or writes it, so do not reuse it. `circuit_run_capacity` is the only user-facing concurrency ceiling, and a hand-built graph with many parallel spawns is bounded only by the agent lease and the optional app-wide pool.

  Circuit runs reserve their declared SpawnAgentNode footprint in a durable run lease, and those leased slots are also counted against the optional app-wide `circuit_agent_pool_size` backstop. This removes the partial-admission deadlock (runs 3+4 of circuit 5) without depending on retired legacy mesh settings; if the optional global pool cannot fit a blueprint's footprint, that run remains pending. With no global pool configured, there is intentionally no additional per-mesh agent-process cap: `circuit_run_capacity` limits admitted runs, not their fan-out. Admission uses worst-case durable lease reservations, while a running Tick uses live circuit-agent counts for the same host-wide pool. Capacity snapshot failures fail CLOSED (zero capacity), loudly logged.
- **Observation preflight and scheduling:** terminal protocol responses (including focus and cursor-position reports) are distinct from prompt edits; only actual input changes its generation/draft fence. Before inference, an unusable report binding becomes a typed, persisted observation blocker. Native finished-turn report snapshots can establish readiness despite stale display status, without inventing background ownership. Classifier and verification jobs run in a bounded FIFO pool (four active, 128 queued), deduplicated by gate/attempt; the worker consumes results with cancellation and freshness fences. Verification worktree paths are exclusive. No DB connection or global registry lock spans job execution. See [session observation](circuit-session-observation.md) for the contract, evidence requirements and remaining fleet-scale work.
- **Projection and delivery reconciliation:** a resumed process may replace status-only evidence from its previous incarnation, but native evidence and conflicts of unknown provenance remain blockers. Legacy projection conflicts require their exact original history digest before reconciliation. Automated Muse follow-ups in an established session require a matching newly appended native run-start record; a terminal redraw or pasted-content box cannot acknowledge submission.
- **Circuit Run History is a fact log, not a transcript (issue #2600):** an observation is a *fact*, and the same fact recorded twice is one fact. `db::circuit::evidence::append_history` declines to write a second observation with the same payload for the same run/node/attempt/source, keyed on the SHA-256 of the payload (`circuit_run_history.detail_sha256`, schema v52). The guard lives in the database, not only in the worker's in-memory projection, because that projection is rebuilt on recovery, reset when a session is replaced, and per-process; a hub that ran before the guard held 1.95M history rows for 115k distinct observations. The other history kinds are a *timeline*: two `step_transition` rows with the same words are two moments in the run's story and are both kept. A one-shot sweep (`db::circuit::history_compaction`, run by the ledger GC worker) collapses the historical copies, keeping each group's first and last row; `services::coordinator_ledger_maintenance` owns the cadence. A repeated observation also does not move the run's revision, so a poll does not make an operator action lose the race against the person's click.
- **Terminal run retention is one vocabulary, and a cancelled run is terminal (issue #2600):** `circuit::vocabulary::RunState::SQL_IN_SWEEPABLE` names the states the retention sweep may delete — `completed`, `failed`, `cancelled` — and `db::circuit::leases` interpolates it rather than re-spelling the literals. Cancelled runs used to be skipped entirely, so their history accumulated without bound (one cancelled run held 306k history rows). The cleanup retry is not what keeps a cancelled run alive: that anchor is the node-scoped `agent_node_lifecycle_leases` row, and the sweep already refuses to delete a run whose step still has a pending cleanup, whatever state the run is in.
- **Codex paste readiness:** the adapter permits inline text, whole-prompt paste markers, and sequences of inline segments and counted paste markers. Each marker accounts for its own burst of Unicode characters; the visible segments must match their corresponding parts of the expected prompt, including CRLF normalization. A smaller marker alone is insufficient. Confirmation uses only output received after staging, then retains the quiet-redraw and input-ownership fences before sending Enter separately. See [Codex paste confirmation](../learning/codex-paste-confirmation.md) for CLI evidence and the limits of rendered confirmation.
- **Circuit completion policy:** `circuit::observation` retains identity-scoped foreground, owned-work and report evidence. Native lifecycle verification remains distinct from report-based progress. A yielded agent may advance from a stable transcript report bound to its session incarnation, input stamp, report revision and publication time; `transcript_reader::report_snapshot` rejects newer tools/input and reuses native turn tracking where available. Commit revalidates the report before taking the DB writer, then fences input/session under the existing transaction boundary. Known unfinished work, evidence conflicts and native human requests block report routing. A generic AwaitingInput projection is a yield, not an indefinite request. Unverified agent steps remain observable for fresh reports and confirmed loss/error; ambiguous external effects never replay automatically.
- **Prompt injection rides the existing two-phase discipline:** the canonical blueprint spawns fresh and delivers the prompt via an InjectPty step gated on `PROCESS_REGISTRY.is_alive` (`AgentReady` event); hand-authored spawn prompts stage as prefill via `SpawnIntent::Loop`. Never bypass `circuit::delivery::write_prompt_to_pty`. Interactive callers use the same seam — the terminal's **Handover to node** hands a selection to an existing agent — and its submit posture is keyed to whether the evaluator *buffers* the target (`circuit::evaluator::is_circuit_piloted`), deliberately not to whether the target has produced output yet: a target no one registered (any node a human spawned) settles on a fixed window and gets exactly one Enter, with no acknowledgement retry and no attention fallback, because no signal exists for it, while a buffered-but-still-silent node — the state Circuit prefill delivery starts in — keeps the retry ladder.
- **Readiness is matched on the span the harness actually draws, where the path collects that evidence at all:** the startup-prefill path (`circuit::launch::marker_hint_for_prefill`) has no adapter-declared policy — a prefill the composer draws in full is confirmed by a distinctive head fragment, and a prefill past `VISIBLE_PASTE_TEXT_LIMIT` (the matching cutoff these heuristics share, not a measured composer viewport) is confirmed by its trailing `TAIL_ANCHOR_CHARS`, because a scrolling input box keeps the tail in view and drops the head. Anchoring a long prefill on its head waits for a marker the harness scrolls out of frame, which burns the whole `WATCH_TIMEOUT` and leaves a staged prompt unsubmitted; an empty marker (a prefill too short to be distinctive) never reports ready, so a quiet workspace-trust dialog is never auto-accepted. The PTY-paste path (`circuit::delivery`) instead follows each adapter's declared `paste_gate_policy`, because only the adapter that owns a spawn's behavior knows how that harness renders a pasted prompt — and only some policies verify that the text arrived at all. `Generic` (the default, and every adapter but Codex and Muse) collects **no** paste evidence: `paste_readiness` leaves it off the rendered gate, and `settle_after_paste` proceeds after `PASTE_ECHO_DEADLINE` for a buffered target or a fixed quiet interval for an unbuffered one, submitting on timing alone. A rendered-gate adapter does verify the draft: `RenderedMarkerOnly` waits for the harness's own `[Pasted Content N chars]` marker, or the complete normalized text at or below `VISIBLE_PASTE_TEXT_LIMIT`, past which that marker is the only evidence it can ever match. `RenderedWithTailAnchor` (Muse) and `RenderedWithSplitMarker` (Codex) additionally accept a long draft's trailing `TAIL_ANCHOR_CHARS`, so only those adapters can confirm a long draft by text.
- **Milestone 3 — circuits react to the world (#1208):** `services::circuit_triggers` owns run *starts*: a GitHub poll pass (every 120s, `maybe_poll_github`, on-demand via `request_github_poll`) ingests labelled open issues/PRs per enabled circuit (`issue:<n>:<label>` / `pr:<n>:<label>` identities — dedupe stays schema-scoped), and the interval pass fires Interval circuits off a cooldown anchored on `MAX(created_at)` of their runs. Trigger sources seed the run's context (`issue.*` / `pr.*`, built by `CircuitContext::with_issue`/`with_pr`), so templates resolve at node execution time. `GithubAction` nodes are instant-completing steps handing an `Effect::CallGithub` to the seam, which resolves owner/repo from mesh origin + target number from context and calls `GitHubClient`; a failed HTTP call fails the step/run loudly. Resilience: `startup_reconcile_pass` runs once per launch and closes the observation-invisible wedge (a Running spawn step with no attached agent = commit-crash gap → fail; lost/archived agent or vanished worktree dir → Lost), while `lost_turn_watchdog_pass` inspects piloted agents quiet ≥60s still marked `running`, then routes a recovered turn through `commands::attention::mark_attention` only after readiness classification and freshness checks (see the quiet-turn boundary below).

  - **Issue-driven Circuit + PR review blueprint:** `CircuitBlueprintKind::IssueDrivenAutopilotReview` is server-owned and requires a GitHub issue-label trigger plus a PR-producing mesh policy. It reuses the issue-review Circuit finish prompt and collaborator gate, then requires the implementation agent's pushed branch/PR before spawning a separate reviewer. The reviewer uses `CircuitGraph::pr_review_prompt()` (the shared `REVIEW_POLICY` plus PR comment scope); it receives both `{{pr.number}}` and `{{pr.url}}`, its terminal report is persisted as `node.reviewer.output`, and the circuit injects that feedback into the implementation agent, which pushes its fixes to the PR. The reviewer is spawned once: the bounded `RetryLimit` re-enters at `re_review`, which re-prompts the same open reviewer, and a `review_round` join feeds either reviewer turn to `ReviewVerdict`, with `retry.*` and `verification.*` context populated as those gates run. Approval closes the reviewer, then `merge` asks the implementer to rebase its branch onto the pull request's base branch, resolve the merge conflicts that rebase produces in favour of the approved work, and squash-merge the PR. The implementer's report is classified (`merge_wait`), then `merge_verify` (`GithubAction::ConfirmPrMerged`, a read-only GitHub lookup) must report the PR merged before `close_implementer` closes the implementation agent. An unmerged PR is a routed `Failed` outcome (not a failed run) and a blocked report skips the lookup: both end in a notification and leave the implementer open. Inconclusive review verdicts park their step as Unverified and notify once; exhausted review retries end upstream in `Failed` with a recoverable checkpoint, so neither path claims approval or erases reviewer evidence. The reviewer has its own worktree, and the blueprint's declared spawns (implementer and reviewer) reserve their agent-lease slots at admission; its run admission is independent of the legacy mesh node setting, with only the optional app-wide Circuit agent pool remaining as a separate process-safety backstop. Mustache autocomplete and the inspector drawer only expose context paths reachable from the selected node's upstream graph.
- **Circuit-agent ownership:** circuit-spawned agents are registered in the shared evaluator but do not create `autopilot_runs` rows. The circuit worker owns their turn classification, per-mesh run and optional global-pool capacity accounting, GitHub-action replay after a restart, and best-effort cleanup when a run fails.
- **Spawn step naming:** a spawn step names its agent node at creation instead of leaving it to the LLM auto-rename. In an issue-triggered run a non-review step gets `gh{N}-{slug}` (as the Issues Probe does), and in a PR-triggered run with no issue it gets `pr{N}-{slug}`. A review step (the built-in `reviewer`, or any step targeted by a `ReviewVerdict` node) gets `pr{N}-review-{slug}` once the run has a PR, `gh{N}-review-{slug}` when it has only an issue, and `review-{reviewed node name}` for the title-bar review preset. A name the Circuit author typed on the step wins, except on the review preset, whose shared graph labels its reviewer "Code reviewer" as a step role rather than a node name. Every name goes through `session_naming::disambiguate_node_name` (`-2`, `-3`, …), because a Worktree Node's name is also its directory and branch; a respawned step agent therefore takes a fresh suffix rather than its predecessor's directory. Steps with no issue, PR or source context keep a random name and the usual LLM auto-rename; derived names skip that rename. The rules are in `circuit_step_node_name` (`services/circuit_worker/spawn.rs`), with `issue_reviewer_node_name` and `agent_reviewer_node_name` in `session_naming/slug.rs`.
- **Quiet is not a finished turn.** The circuit lost-turn watchdog checks readiness before publishing a recovered turn: ongoing background work and unknown evidence leave the node running. It retries at most once per minute and rechecks lifecycle/input stamps, report revision, liveness, and quiet time after classification. This gate is separate from review verdicts, where `WORKING` means changes requested. Attention autoclear cannot undo a false turn after a circuit has already failed and stopped its agent.

- **MiniMax background wake-ups:** a circuit-owned Running or Unverified step can receive one wake-up per attempt when its complete canonical transcript and task store prove that all launched background tasks have terminated and a task ended after the last assistant activity. A truncated tail must read the full history before accepting a wake, because older unfinished work can veto it. Both explicit `started` and timeout `auto_promoted` receipts establish task ownership. Missing state, silent output, an unfinished foreground tool call, a human wait, or a borrowed source agent cannot authorize a wake. A stale Running display additionally requires at least a minute without PTY output. Dispatch rechecks the task ID, lifecycle, report, liveness and input ownership; an uncertain delivery is never replayed. Unverified observation does not advance the ordinary wait deadline. See the [October overnight audit](../archive/2026-10/overnight-circuit-stalls.md) for the failure evidence.

- **Result format repair:** where a phase requires an explicit review or handoff decision, a nonempty result file without a valid final result line follows the same bounded repair path as a missing, blank or invalid-UTF-8 file. It does not fall through to inference. A valid BLOCKED result still waits for the required person; repair cannot infer READY or approval.
- **Shared review contract:** the title-bar review preset and issue-driven review blueprint share `CircuitGraph::REVIEW_POLICY`, feedback instructions, and `ReviewVerdict` routing: approval closes the reviewer and asks the implementation agent to squash-merge (the issue-driven blueprint then verifies the merge on GitHub before closing that agent; the title-bar preset hands its borrowed source back), findings start a fix round on the same reviewer, and an unclear verdict parks the step as Unverified and notifies once. The reviewer remains available for inspection. Local review first asks its borrowed source to publish a PR and waits for that turn, then still inspects uncommitted work; PR review also posts findings to the PR. A completed run hands back every agent its graph did not close, and a failed or cancelled run retires only helper agents (a step agent with a recorded parent, i.e. the reviewer; `RETIRABLE_STEP_AGENT` in `db/circuit/leases.rs`), never the implementation agent: it requests no cleanup lease, and the worker's terminal sweep stops piloting every agent the run referenced. Local source/fix handoffs wait for a finished turn, not proof of task completeness: a clean `Ready`/`Completed` state and fresh report bypass the task classifier, while ambiguous input waits use a review-readiness classifier. Circuit dispatch appends a versioned final-result contract to reviewer prompts (including re-review prompts to an open reviewer), node-review fix feedback and the local publish prompt. `circuit_worker::report_contract` parses one unquoted terminal result line; valid results bypass inference after the ordinary report/session/input preflight, including when the display is still Running. Duplicate, malformed or unknown-version contracts cannot approve; known child work and human requests still block. This establishes report readiness, never native lifecycle verification. A legacy free-form clean reviewer turn (`Ready`/`Completed` with a report) consults the live classifier first; only when that backend is absent or fails does the gate fall back to reading the report's explicit verdict deterministically — approval completes, requested changes start a fix round, blocked or ambiguous reports park for attention — so reviews complete on meshes with no classifier CLI (#1815). The worker uses the app-wide Reviewer provider setting when configured, then falls back to the reviewed agent's harness, while preserving explicit circuit overrides and the existing model/effort cascade. The selected reviewer provider is snapshotted into each run, so later settings changes do not mutate queued work. Reviewer parentage comes from the upstream implementation step or borrowed source and is persisted through `CircuitAgentOwnership.parent_node_id`, so both appear in the same node activity tabs. On exhausted review failure, cleanup stops the live reviewer process while retaining its identity, worktree, association, and report as a recoverable checkpoint; it does not delete the evidence. Startup upgrades exact stock defaults, preserves customized issue-review prompts/topology, and defers active graphs until a later startup.
- **Merge approval evidence:** before delivering the built-in local or issue-review `merge` prompt, the stepper follows completed incoming routes to the approving `ReviewVerdict`. The handoff quotes that decision's evaluated report with its run, review step, attempt, source and report revision; human approval quotes the operator's note instead. A later reviewer message does not replace the evaluated report. The prompt explicitly authorizes merging without another approval request merely because GitHub has no formal approving review; required checks and branch protections still apply. This evidence is added at delivery, including for pinned legacy prompt text. A missing, ambiguous or stale approval parks the merge as an Unverified Checkpoint before a delivery intent is written. Inspect its review evidence before continuing; this checkpoint does not itself approve the work.
- **OpenPr observes a worktree, not an agent process:** its repository seam resolves the upstream spawn association only to inspect the implementation worktree; it is excluded from PTY completion events, lost-turn watchdogs, and agent-lifecycle cancellation. The node carries an explicit `open_pr_policy` (`require_existing` for the review blueprint, `create_if_missing` for ordinary graphs; omitted is the backwards-compatible create default), so the generic action runner never identifies a blueprint by name. The v2 graph migration backfills `require_existing` on persisted review graphs that predate the field. The worker verifies local wrap-up prerequisites, then discovers the PR once using the worktree's actual checked-out branch (not its directory name). Its dirty prerequisite comes from `git::primitives::is_dirty`, which matches `git status` for a Windows directory junction sitting under a directory-only ignore rule (ADR 0044): a worktree that junctions its `src-tauri/target` at the main checkout's cargo cache verifies clean instead of receiving a correction about uncommitted changes that do not exist. Lookup errors remain errors, not evidence that no PR exists; typed GitHub responses preserve PR number, URL, title, and head ref. Existing PR adoption populates `pr.*` before reviewer scheduling; agent completion alone cannot complete this gate.
- **Catalog & contract (#1469):** the shipped blueprint catalog is one canonical list at `circuit::blueprint_contract::BUILT_IN_CATALOG`. Every entry pins marker, allowed triggers, required node ids + edges with conditions, manual-trigger eligibility, and user-visible prompt fragments. The catalog reconciles spec #1205's "three presets" prose with the actual implementation: `WalkingSkeleton` covers *Issue-Driven PR Flow* (Manual / labelled GitHub issue / labelled GitHub PR trigger roots) and *Continuous Looping Pacer* (Interval trigger root) under one skeleton; `IssueDrivenAutopilotReview` is the *PR Adversarial Reviewer* preset. Adding a new variant to `CircuitBlueprintKind` without a `BUILT_IN_CATALOG` entry fails `built_in_catalog_covers_every_blueprint_kind` at `cargo test` time; the matching Probe UI entry fails `tests/unit/circuits-probe-catalog.test.tsx` until the `<option>` lands. Stepper paths are pinned per-blueprint in `stepper::tests`; worker-seam helpers (`observe_close_agent_retries`, `reconcile_spawn_step`) carry the matching walking-skeleton + review-blueprint coverage so the impure seam can't drift from the canonical graph topology.

- **Built-in local review configuration:** new runs pin graph JSON, behavior revision and resolved reviewer launch configurations before acquiring the database writer. Review again increases the failed run's round allowance and sets a review-only graph as the same Circuit Run's executable snapshot. Each replaced graph is archived in per-run snapshot history, preserving the original pinned graph and intervening review snapshots. The reviewer launch configuration stays frozen, and no implementation or publication step is replayed. An explicit extension can admit on a disabled issue-review Circuit, and its formerly owned implementation agent still counts against the optional global pool. Existing Continued Review circuits are consolidated under their original Circuit on startup. Later preference edits apply to future runs. The preset is read-only; its independent editable copy starts disabled with a Manual trigger and no transferred history.
- **Transcript-driven observer recovery:** active circuits recover session identity and restore missing Command Code and Muse passive watchers before waiting for a lifecycle yield (issue #1794 added Muse to the per-harness recovery dispatch). Attaching a circuit to an already-silent source starts its quiet-observation clock without inventing a turn/report boundary. Command Code native committed model messages are distinct from legacy split message records; late watcher replay publishes only the current terminal state, never a historical completion followed by newer work.

## Monitoring and intervening from Probe

Active review runs offer a **Review rounds** selector in the Probe run card
and the agent card's Circuit Overview tab, including while paused.
Choose 1–9 rounds or **Unlimited**; changes save immediately for this run only.
Lowering the limit below the current round lets that round finish and prevents
another round. Unlimited keeps allowing another review when changes are
requested; approval still follows the circuit's normal completion route.
Completed or failed runs keep their history and recovery actions; use
**Review again** to extend an exhausted run.

The allowance lives in `review.round_limit` in the run context (zero means
unlimited), applies only to retry loops containing a review verdict, and leaves
the pinned graph and other retry budgets intact. Each edit appends operator
history, invalidating worker decisions observed before the edit. Views refresh
through `circuit-run-updated`; failed saves report an error and retain the last
persisted value.

The node card of an agent a run owns also carries an Overview tab with the run's
step rail, its actions and a manual push for stuck agent steps; see
[Overview tab](agent-node-circuits.md#overview-tab).

Activity shows admitted runs with issue-led names, elapsed time, current stage,
and a link to the agent currently working. Running and paused runs both count
toward mesh capacity; card order is only a display order and does not assign a
numbered slot to a run. The capacity overview shows spare slots and the
latest worker-recorded admission reason for queued work, including the global
agent pool, disabled circuits and reservation failures. Recorded reasons describe
the last worker check, not a promised start time. Queue retains admission order,
keyboard/drag reordering and cancellation, with issue titles as the primary label.

Run cards start collapsed. Open a card for the step timeline, reports and evidence;
each retained step agent association offers Open, including reviewers absent
from the workspace. The Probe uses the existing agent-history reopen command
to restore closed nodes as suspended, adopts the returned row and focuses its
canvas. Live nodes focus directly; restoration errors remain visible and retryable.
Resolve reveals recovery actions for uncertain or failed steps. Review gates that
are unverified offer explicit **Review passed** and **Request changes** decisions
when no known work/input/evidence blocker remains. History reads check action
availability and prompt freshness without running a scheduler simulation.
Recording Request changes validates that the run scheduler reaches a pending
feedback injection for every modeled outcome and completion order, including
fail-fast siblings while the feedback prompt is still unbuilt. Prompt construction
checks freshness separately because delivery is happening at that point.
Analysis excludes agent reports and notes from its snapshots and memo keys,
shares the graph across branches, and shares one budget across feedback candidates.
It is bounded to 8,192 distinct snapshots, 128 nested completions and 2 MiB of
charged memo-key storage (including active-path copies). These bounds are not
a wall-clock deadline or a total process-memory cap. A resource-limit refusal
asks the operator to simplify the feedback flow before recording the decision.
A Running feedback prompt from an earlier round must finish before
a new decision can target that injection. Joins use retained
parent rows, including earlier attempts; a terminal step reruns only when a
terminal parent's attempt advances past its own. Mutually exclusive branches
cannot combine to satisfy an all-incoming join. A fail-fast
execution error needs a `RetryLimit` recovery edge; without one, the run stops
before feedback can be delivered. Explicit routed results keep following their
configured route: an unmerged `ConfirmPrMerged` check, or a `RetryLimit` that
exhausts a completed-parent feedback cycle. An
inconclusive automatic review emits a circuit
notification and stays unverified with its reviewer available for inspection. It
notifies once
when it first parks for that inconclusive verdict; repeating the same observation
does not repeat the notification. Earlier terminal reviews use Review again to
recover.
Both decisions require a note, validate the current revision and attempt, and record
a human review decision separately from an agent verdict. The revision check ignores
history that only repeats an observation already recorded. A new observation, a step
change, or any other history row still means the run changed and the action must be
refreshed. Completing a step that re-enters a bounded review is offered as **Start
the next review** on the checkpoint and on the manual push while a round remains.
That is a completed edge into a retry gate whose re-entry reaches a review verdict,
and the gate's target attempt is still under the same limit the gate will use. On
the last allowed attempt the same completion is **Record the last round**: recording
it stops the review. When recovery can continue that run — a node review that still
has its implementation agent, or the issue-review blueprint — **Review again** adds
one more round after the run stops. Otherwise the same recording tells the person
to open the implementation agent and inspect the failed step.
**Check again** stays a recheck. **Review passed** and **Request changes** keep
their names. **Start the next review** and **Record the last round** do not approve
the work. The next worker tick
follows the existing approval or feedback branch. Operator findings are appended
to the feedback injection even when its editable prompt omits the reviewer-report
placeholder; human approvals are attributed to the operator in the merge handoff.
**Check again** rereads evidence;
**Review again** on an eligible failed review adds a round. Generic completion
attestation still cannot supply review approval. Other failures retain their
backend-selected retry and already-done recovery actions.

Unverified prompt deliveries offer **Copy payload** and **Sent manually** on
the run card, Circuit Overview and history details. `circuit_prompt_payload`
accepts a `CircuitPromptRequest` (run, step, attempt, expected revision) and
returns the retained prepared terminal text, including a task-file pointer
when staging chose one. It rejects obsolete checkpoints and changed files;
it does not render the template again. Payload files live alongside the run's
handoff files; history keeps their digest and submission identity, not text.
Missing app-data storage preserves automatic delivery but cannot retain this
manual fallback. Existing checkpoints without a retained payload keep their
previous recovery actions.

`manual_delivered` acknowledges the prompt journal without allocating another
submission sequence. Inject steps resume through the normal `PromptDelivered`
transition; initial and continuation prompts resume observing their agent.
The already-armed handoff marker and result file remain intact. Downstream
waits can inherit the newest submission and native turn binding from a retained
ancestor attempt on the same agent; sibling steps and old attempts cannot supply
that binding. Ancestor and observer attempt counters need not match. Binding
within the same step still requires an exact attempt match, including in bounded
cycles. The action bypasses stale terminal ownership, resolves input waits
only through the correlated turn start (or preparation time when unavailable),
and preserves later input requests, work evidence and review requirements.

History shows issue-led outcomes, PR links when retained, and a **Shipped** label
only when the run recorded GitHub merge confirmation. Review approval alone is
not shipment. Search covers retained issue and PR fields plus `source.name`; agent reports and internal status values are excluded. Details and technical
history stay behind disclosure; the history window and retention policy still
apply. Manage owns capacity, enable/disable, flow editing, manual triggers and
circuit creation. Its creation form expands inside the scrolling body.

## Circuit architecture (spec #1205)
- **Graph authoring and compatibility have separate owners.** `circuit/model.rs` owns the AST, serialization and validation; `circuit/blueprints.rs` owns canonical builders and stock prompts. Migrations and canvas saves use `circuit/stored_graph::upgrade`, which owns the first-turn, verdict, prompt-contract, feedback-route, publication and merge upgrade order. Storage context limits applicability: local-review copies keep their topology, active legacy prompt contracts defer until their runs finish, and pinned run snapshots receive only the dead feedback-route repair. Migrations pin an existing run's graph before updating its circuit row. An upgrade that introduces a node must introduce the edges its own historical shape shipped with, not the ones today's blueprint has: copying those back points an older graph at a node the upgrade never adds, and the next upgrade in the chain finds no edge to rewire.
- **A run's context has a small half and a bulky half (issue #2601).** `autopilot_circuit_runs.context_json` is rewritten as one blob on every advance. When it carried full agent outputs and evidence blobs, the run row overflowed its page, every advance re-serialised tens to hundreds of kilobytes, and every query that inspected the context had to parse all of it. `db/circuit/artifacts.rs` owns the split: values above `BULKY_VALUE_BYTES` move to the `circuit_run_artifacts` table, keyed by run, node and attempt, and the column keeps the decision-relevant half plus `context.artifact_digest` — a fingerprint of the stored bulky set, so the worker's freshness fence still sees a bulky change. A run with nothing bulky in it carries no digest, so its context stays exactly what it was. The split happens inside `ledger::commit_circuit_advance_inner`, the engine's single atomic commit point, so a crash can never leave a context half-split. A bulky value is written once, when it changes; a read joins the two halves back together. The wait paths (`node.*.continuation.delivery`, `node.*.observation_blocker`, `node.*.capacity_wait`, `node.*.wait.*`) always stay in the column, because the wait history is written by comparing the previous and the next context. Clearing a node's working state — the operator's step recovery, a review extension — clears its artifacts with it: a write replaces the run's bulky set, and a value the new context does not mention is unchanged rather than gone, so those two paths delete the stored values before they write. That rule reaches the stepper: removing a key from a run's context clears it when the key is small, and a bulky key has to be cleared with `delete_node_values` or `delete_values_with_prefix` beside it, or the stored copy comes back on the next read. A reader that wants only the decision-relevant half reads the column alone — the worker's freshness fence compares the column with itself and must never see a joined context — while the operator-facing projections (the run card, the pending queue, the circuit ledger, the Agent Node card's Overview tab) rejoin the two halves, because the Probe reads a review report and the issue body it searches by out of the run's `context_json`. The digest is a storage fingerprint, so the joined views drop it. The side table carries no index beyond its primary key: every read filters by `run_id` and the node-scoped delete uses a key-prefix range, so an index nothing reads would be a page written on every first insert. Every path that drops a run drops its artifacts with it — the retention sweep, the Circuit delete and the Mesh delete — because SQLite's `ON DELETE CASCADE` does not fire when the `foreign_keys` pragma is off. The lineage flags of issue #2234 stay in the column: they are small, and they are what queries filter on.
- **Capacity has separate run and agent leases (ADR-0028).** `meshes.circuit_run_capacity` admits pending Circuit Runs. Before admission, the worker reserves the blueprint's declared SpawnAgentNode footprint in `autopilot_circuit_run_agent_leases`; every spawn consumes that lease and remains bounded by the optional app-wide `circuit_agent_pool_size` when configured. Admission counts durable worst-case leases; a running Tick counts live circuit agents when applying that optional host-wide pool, so the two snapshots are intentionally not interchangeable. The legacy `meshes.autopilot_concurrency_limit` is not a circuit gate. Do not infer run authorization from mutable step agent ids.
- **The pending queue is durable and user-controlled.** `autopilot_circuit_runs.queue_position` is scoped per Mesh; worker admission and the Probe's complete queue both read it nearest-first. Moving a pending run swaps adjacent positions. Cancelling first commits the terminal `cancelled` state, then retires attached Agent Nodes; the worker rechecks durable state before every external effect. Cancellation and circuit deletion quiesce in-flight two-stage spawns under a worker barrier, and an aborted spawn retains its step ownership until process/worktree retirement succeeds. Circuit deletion disables triggers, applies the same cleanup contract to active and terminal runs (including retrying cleanup for already-cancelled runs), and removes the circuit ledger only after every retirement succeeds; failures retain the disabled ledger as the retry anchor.
- **Pure core / impure seam split:** `circuit/stepper.rs` computes `advance(run, event) -> Transition` without SQLite or network. `services/circuit_worker/mod.rs` owns the run loop and transition commits. `services/circuit_worker/dispatch.rs` owns effect application: the gate, the journal claim, and dispatch through an effect host. The worker commits via `db::commit_circuit_advance` BEFORE executing external effects. `admission.rs` owns run admission and capacity snapshots, `turn_classify.rs` owns report interpretation and quiet-turn recovery, and `restart.rs` owns startup reconciliation and observer reattachment. `observation.rs` combines their observations into ordered events for the existing `RunView` seam. Its lazy live adapter preserves the order of native receipt reads, agent checks, job polling, approvals, capacity and waits; unit tests supply observations and time without SQLite, PTYs or classifiers. A literal event snapshot pins that ordering across extraction, while worker integration tests retain the real persistence checks. Admission reservations and running live-agent counts remain distinct snapshots of the same capacity policy. Circuit persistence is `db/circuit/{ledger,queue,leases}.rs` (issue #1660); `CircuitTriggerKind` lives on the graph model, not the IPC adapter.
- **Recovery uses the same transition invariants.** `set_step` owns inherited attempt changes and persists the fresh-attempt reset of outcome/error alongside the in-memory reset. Report readiness may override a stale Running display; durable completion checks session identity and input/report freshness without reinstating that display-status gate. Operator completion eligibility is shared by the evidence view and command and never fabricates native lifecycle evidence. OpenPr reconciliation uses a persisted per-attempt lookup allowance and never replays creation.
- **Effect replay policy:** spawn, PTY prompt, and GitHub effects claim a typed durable journal entry before external dispatch; an unknown result never replays automatically. Classifier continuation uses its pending/claimed context fence. `SetNodeStatus` commits with its completed step in one SQLite transaction; close effects retry idempotently while their association remains; notifications are transient. The complete per-effect and review-continuation inventory is `docs/development/circuit-effect-recovery.md`.
- **Circuit-run attention is derived; acknowledgement is persisted.** "Needs attention" is not a stored flag — it is recomputed from run state, review verdict and step status (`runNeedsAttention`), so a run the person has already handled by hand keeps asking. `autopilot_circuit_runs.attention_dismissed_at` (v48) records that the user has seen the remainder: `runNeedsOutstandingAttention` is the notification predicate, while `runNeedsAttention` stays the diagnostic one so a run card keeps stating why it wants attention. Dismissal changes no run state, step or verdict. NULL is the default and means "still outstanding"; the acknowledgement is one-way, because no command writes it back. Two predicates rather than one is deliberate — collapsing them would either hide the reason or keep re-sorting the run to the top.
- **The bulk acknowledgement's count is not the ledger's count.** The ledger deliberately surfaces at most `RECOVERY_RUNS_PER_CIRCUIT` (50) attention runs per circuit so a long-dead circuit cannot stream its whole lifetime, but `dismiss_all_circuit_run_attention` reaches every outstanding run on the mesh. Counting the ledger payload would therefore read "Dismiss 50" and then clear 75 — 25 of them never shown to the user. `count_circuit_run_attention` answers the unbounded number instead, and both it and the mutation share one `OUTSTANDING_ATTENTION_RUNS` predicate so the confirmation names exactly the rows the command changes. Two properties that predicate must keep: it selects `DISTINCT` run ids, because the joins are one-to-many and `COUNT(*)` over joined rows would count a three-step run three times; and the toolbar shows no bulk action at all when the count is unavailable, because a windowed substitute is precisely the understatement it exists to prevent. The count is stored alongside the mesh id that produced it and the toolbar renders it only for that mesh; it is also dropped on every mesh switch, so the control stays hidden until the current load supplies a count. Scoping alone is not enough — on an A→B→A round trip the original mesh's id matches again, and a count retained through a failed fetch in between would describe runs that could have changed underneath it. An armed confirmation is cleared on the same switch. The count is fetched in parallel with the ledger snapshot, not after it, so the runs and their bulk action appear together instead of the toolbar flashing runs-without-action. A bulk acknowledgement changes no run state, so it emits `circuit-runs-attention-dismissed` rather than `circuit-run-updated`; the Probe subscribes to it so a view that did not perform the clearing still refreshes.
- **Operator attestations accept an optional note, except a review verdict.** `recover_failed_run` and `record_outcome` record their action with an optional `reason`; the attestation is written either way, and a blank note produces its own fixed wording per branch instead of an empty sentence. A review verdict (`review_pass` / `review_fail`) is the exception: it records a person's judgement about someone else's work, so the evidence is part of the verdict and `record_outcome` rejects a blank one. `checkpointActionNeedsEvidence` is the single definition of that split, shared by both the run card and the evidence history. Requiring prose everywhere blocked people who had genuinely already done the work and had nothing further to add; requiring none of it would record verdicts with no basis.
- **StepStatus vs StepOutcome are distinct.** `StepStatus` is the lifecycle column (queued / running / blocked / completed / failed / cancelled). `StepOutcome` routes edges (completed / failed / cancelled / blocked / working / green / red). A Blocked status parks a live step; a Blocked outcome is terminal classifier routing. `commit_circuit_advance` uses `StepOutcome::is_terminal_db_str` for terminal stamps.
- **RetryLimit semantics (#1207):** max_retries is the TOTAL allowed executions of the failing step, not retries beyond the first. With max_retries=3, attempts 1/2/3 all run; budget exhausted at attempt == max. Failed step is reset to Queued with attempt + 1, outcome/error cleared, started_at restamped via the fresh_attempt SQL path. The gate's own step is re-armed (Queued + fresh_attempt) when the same upstream fails again later so it can fire repeatedly across loops.
- **Reactive PTY wakeups (#1207):** `circuit::evaluator::on_output` wakes the circuit worker after each PTY chunk. `classify_step_turn` checks evaluator freshness and report binding before inference; validated native finished-turn evidence can establish readiness despite a stale Running display. Other recovery paths retain their evidence requirements. Freshness probes are scoped to the run, gate, and attempt, while durable context deduplicates the report that each gate consumed; a short cooldown retries a transcript that is published just after a yield. Failed classifications retry after 60 seconds even without new output (a classifier that times out backs off 1, 3, 10 and 20 minutes instead, see the circuit recovery bullet below), up to five failures per gate attempt. Durable exhaustion fences ordinary classification and quiet-turn inference across restart and fresh reports; only explicit evidence recheck resets the budget. The last sanitized backend error remains visible. The independent Circuit classifier selection accepts host-native configurations with an adapter-owned background inference recipe and saved model/effort; Codex runs ephemeral read-only inference outside the repository with shell and multi-agent tools disabled; an unavailable classifier is never routed as `WORKING`, and empty/suppressed reports are ignored. Parked gates retain an explanation in the step ledger. Every drive restores evaluator ownership for all attached agents, including completed spawn steps that still supply downstream classifiers. Transcript recovery uses an assistant-record revision (record position plus normalized assistant-text hash, not file mtime); prompt injection persists the preceding revision in the same transition commit before delivery so a permission yield or resume redraw cannot reuse it. Providers without recoverable transcript evidence require a live turn boundary before replayed output is trusted. See [the September 5 classifier-recovery investigation](../archive/2026-09/circuit-classifier-recovery.md).
- **Review handoff and native completion:** initial and feedback gates require identity-bound lifecycle and report evidence. A Ready status cannot authorize initial review handoff. The Codex native adapter exposes explicit foreground turn completion; rollouts do not establish complete owned-work coverage. Recovery rejects newer transcript activity and atomically matches process incarnation, input ownership, last submission time and durable lifecycle stamp. Acquire SQLite before the per-agent input guard; global registry locks never span database work. Native Claude receipts are bound to a Buildmesh submission by content and ordering, not arrival: a `UserPromptSubmit` hook echoes the verbatim `prompt` and names the turn with `prompt_id` (Claude Code v2.1.196+), and Buildmesh matches that echo against the digest of the submission it recorded before writing to the PTY, while that submission is still the newest for the agent. A `Stop` inherits the binding by turn id. Receipts that cannot be bound this way - no `prompt_id`, no matching echo, a superseded submission, an ambiguous claim - keep reduced confidence. See `docs/learning/claude-code-harness-capabilities.md`.
- **Paused runs still occupy circuit-agent slots.** `count_active_circuit_agent_nodes_total` includes running and paused runs. The stepper stops scheduling while paused; lifecycle events may finish the current step, but scheduling resumes only after `Resumed`.
- **Zombie agents are reaped, never left running (issue #1793).** A self-throttled sweep on the worker tick (`services::circuit_worker::zombie_sweep`) transitions circuit-piloted nodes stuck `running` with no session identity and no readable report past 15 minutes to the terminal `Lost` status, then surfaces each transitioned node through `agent-lifecycle`. It follows the three-phase DB pattern — scan under a reader, transcript read and notification dispatch lock-free, batch write under the writer — and is scoped to nodes referenced by `autopilot_circuit_run_steps`, so a user's interactive node (e.g. a `terminal` shell with no captured identity) is never reaped. Per-agent observation is cooldown-limited. The circuit observer maps `Lost` to `AgentLost`, so an attached step cancels promptly instead of waiting out the first-observation window.
- **Circuit recovery is bounded and durable.** Missing session identities are retried through adapter-owned metadata discovery with a generation-checked conditional write. Wait clocks persist in run context per gate attempt: 15 minutes after yield (a harness may declare a shorter budget for a yield with no classifier verdict yet; once the classifier reports work remaining the wait widens to 15 minutes), two hours without a new report while active, and a 15-minute first-observation fast-fail that ends a busy step whose agent has produced no session identity or report yet instead of holding the active budget, unless the step pins its own `timeout_seconds` (issue #1791); human approval gates do not expire; pause/resume suspends and renews the allowance. Classifier outages stop after five attempts; once exhausted, only an explicit evidence recheck resumes classification. A classifier that *times out* (a wedged CLI start-up, as in run 399, where every `mcode exec` hung for 28 minutes and then recovered by itself) waits 1, 3, 10 and 20 minutes between attempts, about 34 minutes in all, so a stall of that length no longer parks the gate (the failure time is persisted per gate attempt, so an app restart does not shorten the wait); any other failure (a bad login, a missing binary, an unrecognised verdict) retries every minute and surfaces its diagnostic sooner. Only an explicit circuit CONTINUE verdict can prompt an owned agent, at most twice per attempt; pending delivery replays, while claimed delivery waits for evidence rather than risking duplicate input. Delivery rechecks the process/turn stamp and report revision. Failure/cancellation commits cleanup intent together with terminal state; a retry sweep protects borrowed/active references and retention preserves unfinished cleanup. See [the September 6 circuit autonomy audit](../archive/2026-09/circuit-autonomy-audit.md) for evidence and limits.
- **Handoff files (issue #2134).** `circuit::handoff` owns each run's folder under the app data dir (`circuits/runs/run-<id>`). Every circuit prompt, whether the initial prompt of a spawn or a prompt written into a running agent, is saved in full as `<step>-attempt<n>.prompt.md`. When the prompt is longer than the inline paste limit, the terminal receives a one-line pointer to that file instead. The submission digest covers the text actually delivered, so native-hook correlation still matches. If the file cannot be written, the prompt is pasted inline as before. WSL agents receive the `/mnt/` form of each path. A prompt with a result contract also asks the agent to write its final report to `<step>-attempt<n>.result.md`, and only once it has finished; so does every prompt to a harness with no lifecycle of its own, for which the settled file is the turn signal (see [result-file turn completion](circuit-session-observation.md#result-file-turn-completion)). A per-agent turn marker (`agent-<id>.turn`) names the prompt and result pair the current turn owes. When that result file exists, it is the report that is interpreted and forwarded as the step's output, in place of the transcript. Its classification binding fingerprints the result contents and retains the admitted turn's session and input boundary, including the transcript guard when present; changes to either file invalidate the decision before commit. Receipt-backed handoffs bind the result at the current gate while preserving the native receipt's original owner and evidence. Continuation delivery still compares the transcript revision rather than the result revision; a harness without a transcript report compares the revision named by the result file its turn owes. A result file or retained transcript that changes during the read is retried on a later observation without classification, reminders, repair-counter changes or needs-input. An ordinary unreadable result file makes the checkpoint visibly Unverified with its path and read error, without classifying the transcript or consuming a reminder. Failed reads are counted durably per step attempt; the third failed probe raises a needs-input notification once, and the checkpoint stays Unverified until usable evidence arrives. Further probes can recover a repaired file, but do not repeat attention or promise automatic resolution. Result instructions require UTF-8 (Windows PowerShell must use Set-Content -Encoding UTF8); an optional UTF-8 BOM is accepted. A finished turn that still owes a missing, blank or invalid-UTF-8 result file gets a reminder through the claimed continuation lifecycle, at most two per step attempt and one per observed turn (report revision plus agent turn stamp, so an agent that takes a turn without producing a new report is still counted). After the second, or when a reminder could not be delivered and nothing has changed since, the step is Unverified and a needs-input notification is raised. Before any continuation is delivered, the turn's existing result file is archived as `<step>-attempt<n>.result.superseded-<k>.md` and the continuation asks for the result again, so an earlier turn's result is never read as the continuation's. Turns waiting on a person (awaiting input) are not reminded. The stepper stays pure: file existence arrives as an observed `ResultFileMissing` event. The periodic circuit-run maintenance pass removes a run's folder once the run no longer exists.

`preferences::spawn_configurations` owns named, capability-validated launch overrides scoped to one Spawn Option. Configurations live in application preferences; the backend menu includes each option's saved choices for mobile, while desktop management reads the same collection through IPC. The shared editor creates and edits configurations from Settings and spawn menus. Launch targets include unattached credentialed providers; saving a new route and recipe uses one preference transaction. Draft verification resolves the selected model without persisting the draft; verification records distinguish endpoint/model/runtime so checking one recipe does not replace another model's proof. Provider model metadata is independent of tier remaps, and allowed efforts intersect provider/model/surface metadata with harness capabilities. New-node creation commits the selected snapshot in `agent_nodes.spawn_configuration` in the same transaction as the node. Explicit per-call overrides win; omitted native fields retain the mesh/application/native cascade, while proxy models default to their route and do not inherit native harness model/effort defaults. A resolved proxy model reaches Codex as a single `--model`: `agent::spawn::command::build_spawn_command_prepared` folds the routing descriptor's model into the resolved config before `default_prepare` composes the recipe, so the adapter remains the single owner of the model flag and the orchestrator layer adds only `--profile` and the reasoning `-c` keys. The fold is load-bearing in both directions: the generated `<profile>.config.toml` carries only `model_provider`, so an empty cascade model would leave Codex on an OpenAI model against a foreign endpoint, and a second occurrence is rejected by the CLI as a repeated argument. Resume reads the snapshot, not the editable preference. A provider change cannot reuse another Spawn Option's snapshot.

## Legacy automation upgrade compatibility

Legacy Autopilot is removed from the application. Only `db::legacy_retirement` and `services::legacy_retirement` handle the one-way upgrade and retry cleanup of persisted legacy nodes. Existing nodes, worktrees and history remain available; legacy columns and ledger rows are never launch configuration or capacity inputs. Retired configuration is not loaded into Circuit settings. Persisted `AutopilotCircuit` names and graph keys belong to Circuit schema compatibility, not the legacy runtime.
