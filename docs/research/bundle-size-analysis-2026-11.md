# Bundle size analysis — frontend entry chunk and Rust release binary

## Scope and method

Question asked: where do barrel-style imports pull whole libraries into the
bundle, and what are the biggest size reductions available without changing
behaviour?

Baseline: commit `6ce49006` (`perf(terminal): bound raw Channel decode backlog`),
branch `perfumed-grand-bunny`, worktree `F:\src\buildmesh\.worktrees\perfumed-grand-bunny`.
Host: Windows 10.0.28120, Node v24, Rust 1.95.0 (`x86_64-pc-windows-msvc`),
MSVC 2019 toolchain.

Method — nothing below is estimated from a dependency list; every number comes
from a built artefact:

- **Frontend.** `npx vite build` (Vite 8 / rolldown) plus `npx vite build
  --sourcemap`. The sourcemap's `mappings` were decoded (VLQ) and every
  generated byte attributed to its source module, then grouped by the npm
  package that owns that module. Chunk reachability was computed over the
  built chunk graph: a chunk is *eager* only if the entry chunk reaches it
  through static `import` edges.
- **Rust.** `cargo rustc --release --bin buildmesh -- -C link-arg=/MAP:...`
  produced an MSVC linker map. The map names the contributing object file per
  symbol, so bytes are attributed to the owning crate; symbol size is the
  distance to the next symbol in the same segment. Release profile is the
  repository's: `strip = true`, `lto = "thin"`, `codegen-units = 16`,
  `panic = "abort"`.
- **Deltas** were measured by building the baseline, measuring, applying the
  change, rebuilding and measuring again (`git stash` between the two builds).

## Headline

Frontend, desktop entry chunk. "Before" is the baseline build at this commit;
"after" is the same build with the lazy boundaries and module splits described
below, measured with the same script:

| Measure | Before | After | Delta |
|---|---:|---:|---:|
| entry chunk, raw | 1057.3 kB | 619.4 kB | **−437.9 kB (−41.4 %)** |
| entry chunk, gzip | 312.6 kB | 182.2 kB | **−130.4 kB (−41.7 %)** |
| eager JS (all chunks), raw | 1204.7 kB | 771.7 kB | −433.0 kB (−35.9 %) |
| eager JS, gzip | 364.5 kB | 236.3 kB | −128.2 kB (−35.2 %) |
| eager CSS, raw | 110.7 kB | 95.4 kB | −15.3 kB |
| **first load total, raw** | **1315.3 kB** | **867.1 kB** | **−448.2 kB (−34.1 %)** |
| **first load total, gzip** | **383.0 kB** | **252.6 kB** | **−130.4 kB (−34.0 %)** |

An independent reviewer re-measured the "after" side from the same build and
got 867.6 kB raw / 252.5 kB gzip — the two agree to within 0.5 kB.

The Rust release binary is separately reduced by the two dependency trims in
Part B: **−689 152 bytes (−2.5 %)**.

What this does *not* do is shrink the shipped bytes. Splitting moves code out
of the entry chunk into chunks that are still in `dist/` and still embedded in
the executable; the installer is unchanged (desktop `dist/` 2 267 kB → 2 274
kB, mobile 816 kB → 818 kB). The win is what the webview parses and executes
at launch, and what it holds in memory before the user opens anything.

The largest Rust-side item is not a dependency: `buildmesh_lib`'s own code is
13 249 kB — 62.1 % of all attributed symbol bytes. The largest dependency
items are bundled SQLite (1410.7 kB) and bundled libgit2 (909.0 kB), which are
inherent to the product.

### A1. The circuit editor drags React Flow + dagre into the entry chunk — 217 kB

Chain (static imports only):

```
src/main.tsx
  -> src/App.tsx
    -> src/components/AgentNodeView/AgentNodeView.tsx:14
      import { CircuitEditorOverlay } from '../Circuits/CircuitEditorOverlay';
        -> src/components/Circuits/CircuitFlowEditor.tsx:32
          import { ... } from '@xyflow/react';
```

`CircuitEditorOverlay` is mounted **conditionally** — `AgentNodeView.tsx:409`
renders `{circuitEditorOpen && <CircuitEditorOverlay />}` — but it is imported
statically, so everything it reaches is in the entry chunk.

What it pulls in: `@xyflow/react` 78.3 kB + `@xyflow/system` 43.0 kB +
`d3-selection/-transition/-zoom/-color/-interpolate/-drag/-dispatch/-timer`
49.7 kB + `dijkstrajs` 1.1 kB = **172.1 kB**, plus `@dagrejs/dagre` 45.5 kB
(reached through `circuitGraphModel.ts:14`, `import dagre from '@dagrejs/dagre'`).
The React Flow stylesheet (`import '@xyflow/react/dist/style.css'`) also lands
in the **entry stylesheet**, so 15.6 kB of CSS is fetched on every launch.

Fix — a lazy boundary, the same pattern `ProbePanel.tsx:378` already uses for
its tabs:

```tsx
const CircuitEditorOverlay = lazy(() =>
  import('../Circuits/CircuitEditorOverlay').then((m) => ({ default: m.CircuitEditorOverlay })),
);
```

Measured result: the editor and its whole library stack move into one
212.8 kB chunk (`CircuitEditorOverlay-*.js`) that is fetched only when the
user opens the circuit canvas, and 15.6 kB of CSS moves out of the entry
stylesheet into `CircuitEditorOverlay-*.css`.

### A5. A barrel that pulled a 25 kB generated table — fixed

`src/types/generated/HarnessCapabilitiesTable.ts` is 873 lines / 24 913 bytes
of generated data, and 14.3 kB of it was in the entry chunk. The path was:

```
src/App.tsx
  -> src/components/AgentNodeView/AgentNodeView.tsx
    -> src/components/AgentNodeView/AgentReviewButton.tsx:8
      import { blocksReviewCircuit } from '../Circuits/harnessCapabilities';
```

`src/components/Circuits/harnessCapabilities.ts:20-26` was a barrel that
re-exported `HARNESS_LABEL`, `HARNESS_PROFILE_ALIASES` and the id type straight
from the generated table. One boolean predicate (`blocksReviewCircuit`) dragged
the whole catalogue in. `AppSettings/ProvidersPane.tsx:27` imported the same
barrel.

**Fixed** on both sides:

- The Rust exporter (`src-tauri/src/agent/harness_catalog.rs`) now emits a
  second artifact from the same rows —
  `src/types/generated/HarnessReviewEligibility.ts` — carrying the id
  vocabulary, the profile-alias table and the four review-circuit eligibility
  flags. The full table re-exports the id vocabulary from it, so there is
  exactly one *TypeScript declaration* of it; the full table's payload still
  carries a copy of the id list, because the Rust and docs gates read it from
  the emitted JSON. A Rust test asserts the two artifacts agree flag for
  flag, and the frontend test
  `tests/unit/circuits-inspector-capabilities.test.ts` asserts the same from
  the TypeScript side.
- The predicate moved to
  `src/components/Circuits/harnessReviewEligibility.ts`, which reads only the
  narrow artifact. `AgentReviewButton.tsx`, `AppSettings/ProvidersPane.tsx` and
  `mobile/screens/StartReview.tsx` import it from there; the Inspector's
  lookup helpers stay in `harnessCapabilities.ts`, whose only importer is the
  Inspector (`Circuits/InspectorPanel.tsx`).

The full catalogue is therefore **not eagerly reachable**: the entry chunk
carries only the narrow artifact. It is reachable from two *lazy* entry
points — the Inspector, and `src/lib/archiveProvenance.ts`, which reads
`HARNESS_LABEL` and `HARNESS_PROFILE_ALIASES` and is reached from the Probe
tab `ArchivedNodesTab` → `AgentHistoryTab`. Sharing the catalogue with the
Probe tab costs nothing extra, because the Inspector needs it anyway.

The mobile SPA carries both artifacts (it needs the labels for the archived
nodes screen and the eligibility flags for the review screen), so it grows
2 kB — 816 kB → 818 kB.

### What was implemented

The three lazy boundaries live in one module,
`src/components/lazySurfaces.ts`, so there is a single place that owns the
rule "a surface belongs here when it is mounted conditionally and big enough
that deferring it is worth a chunk boundary":

```ts
export function loadCircuitEditorOverlay(): Promise<{ default: typeof CircuitEditorOverlay }> {
  return import('./Circuits/CircuitEditorOverlay').then((m) => ({ default: m.CircuitEditorOverlay }));
}
export const LazyCircuitEditorOverlay = lazy(loadCircuitEditorOverlay);
```

Each loader is also reachable by name through `preloadLazySurfaces(...)`, so a
test can await the chunk before it makes a synchronous assertion — the same
`preload` seam the Probe tab registry has (`src/lib/probeContext.ts`).
`AgentNodeView.tsx` and `TitleBar.tsx` import the lazy components and wrap them
in `<Suspense fallback={null}>`.

`scripts/check-bundle-composition.mjs` now lists the three surfaces in its
`FORBIDDEN` list, so a static import of any of them fails the build again
rather than quietly restoring the entry-chunk cost.

**Behaviour impact: none.** All three components were already conditionally
mounted; the only change is that their code arrives when they are first
shown. The one visible consequence is a one-frame blank while the chunk
loads, which is why the `Suspense` boundary is required. The chunk comes from
the app's own embedded assets, so the load is a local read rather than a
network round trip.

Tests changed for the same reason — a `React.lazy` surface is async UI, so the
assertion has to wait for the content rather than assume the import resolved
inside the click's `act()`:

- `tests/unit/title-bar.test.tsx` and `tests/unit/title-bar-compact.test.tsx`
  now use `findByRole('dialog', …)` and preload the two modal chunks in a
  `beforeAll`, the way the Probe suites preload their tabs
  (`tests/unit/helpers/preloadProbeTabs.ts`).
- `tests/unit/lazy-surfaces.test.ts` (new) pins each loader to the component
  it must resolve — a renamed export otherwise resolves to `undefined` and the
  surface renders nothing, with no failure until a user opens it.
- `tests/unit/circuit-graph-model.test.ts` imports `layoutPositions` from its
  new home.
- `tests/unit/circuits-inspector-capabilities.test.ts` imports the predicate
  from the new module and asserts the narrow artifact mirrors the full
  catalogue flag for flag.

### Two bundles, one payload

`src-tauri/tauri.conf.json` sets `"frontendDist": "../dist"`, and
`src-tauri/src/lib.rs:168` calls `tauri::generate_context!()` — so the whole
desktop frontend is compiled into the executable. The asset paths are present
in `buildmesh.exe` in plaintext and the file bodies are brotli-compressed
(Tauri 2 does this; that is why `"xyflow"` and `"react-dom"` do **not** appear
as strings in the binary).

| Payload | Raw | In the .exe |
|---|---:|---:|
| desktop `dist/` (Tauri, brotli) | 2 267 kB | ~580 kB |
| `dist/mobile/` (`rust-embed`, **uncompressed**) | 816 kB | **816 kB** |
| total frontend inside the 25.7 MB exe | 3 083 kB | ~1 396 kB |

Two consequences:

1. Code-splitting does **not** shrink the installer — the deferred chunks are
   still shipped and still embedded. It shrinks *what the webview parses and
   executes at startup*, which is the number in the headline table.
2. The mobile SPA is embedded **raw** by `rust-embed` (see R1 below for a
   one-line fix worth ~590 kB).

### R1. The mobile SPA is embedded uncompressed — fixed, ~590 kB

`src-tauri/src/http/assets.rs:12-14`:

```rust
#[derive(rust_embed::Embed)]
#[folder = "../dist/mobile"]
struct MobileAssets;
```

`rust-embed = "8"` was declared with default features, so the 816 kB mobile
bundle was stored **raw** in the executable. `rust-embed` has a `compression`
feature (deflate-based):

```toml
rust-embed = { version = "8", features = ["compression"] }
```

Measured: the mobile bundle compresses to 227 kB, so the executable loses
~590 kB of asset bytes. One thing makes the change behaviourally a drop-in:

- The application reads assets through `MobileAssets::get(path)`
  (`assets.rs:158`, `:242`), and `get()` returns the **decompressed** bytes
  when the `compression` feature is on. `serve_asset`'s length and range
  logic is therefore unaffected.

**It is not free, and it does add supply-chain surface.** `rust-embed`'s
`compression` feature pulls in `include-flate`, whose default features are
`["deflate", "zstd"]`. That is eight new entries in `Cargo.lock`:
`include-flate`, `include-flate-codegen`, `include-flate-compress`,
`libflate`, `libflate_lz77`, `zstd`, `zstd-safe` and `zstd-sys` — the last
being a **C library** compiled through `cc`. The asset decompressor is
`libflate`; the zstd decoder is linked but never used, because rust-embed
requests plain `include-flate` and the application only ever writes deflate.
So this trim trades ~590 kB of raw assets for ~306 kB of new `.text`, and it
grows the dependency tree that `npm run check:audit:rust` gates. (The
`flate2` / `miniz_oxide` already in the tree come from `syntect`'s
`dump-load` feature, but `flate2` is *not* the decompressor `rust-embed`
uses.)

The measured before/after pair (two release builds three minutes apart, same
source otherwise) is:

| Build | `buildmesh.exe` |
|---|---:|
| before (both trims reverted) | 27 833 856 bytes |
| after (both trims applied) | **27 144 704 bytes** |
| delta | **−689 152 bytes (−2.5 %)** |

That is the *net* of the assets saved and the decompressors added, across
R1 and R2 together.

### R2. `syntect` pulls the Oniguruma C regex library — fixed, ~150 kB

`Cargo.toml:52` declared `syntect = "5"`. syntect 5.3.0's feature graph:

```
default      = ["default-onig"]
default-onig = [parsing, default-syntaxes, default-themes, html,
                plist-load, yaml-load, dump-load, dump-create, regex-onig]
default-fancy = [ ... same ... regex-fancy ]      # <- pure Rust instead
regex-onig   = ["onig"]
regex-fancy  = ["fancy-regex"]
```

So the default feature set dragged in `onig` + `onig_sys` (the Oniguruma C
library, **151.5 kB measured**), `yaml-rust` (YAML theme/syntax loading, never
used) and `plist` (plist theme loading, never used).

The application only uses `SyntaxSet::load_defaults_newlines`,
`ThemeSet::load_defaults` and `syntect::html` (`src-tauri/src/diff/highlight.rs:16-26`,
`:80`) — no YAML, no plist, no dumps written.

```toml
syntect = { version = "5", default-features = false, features = ["default-syntaxes", "default-themes", "html", "regex-fancy"] }
```

`default-syntaxes` and `default-themes` imply `parsing`, `dump-load` and
`dump-create` (so `bincode`/`flate2` stay), but `onig`, `yaml-rust` and
`plist` leave the tree — `plist` remains only as Tauri's own dependency, not
through syntect. `fancy-regex` arrives, but
it is built on `regex-automata`, which is already present (477.6 kB) via
`regex`. Net expectation: **~150 kB off the binary**.

**Risk, and how it was checked.** `fancy-regex` implements a subset of
Oniguruma, and syntect compiles a grammar's regexes **lazily** and `.expect()`s
on failure (`syntect-5.3.0/src/parsing/regex.rs:70`,
`expect("regex string should be pre-tested")`). So a grammar whose pattern the
active engine rejects is a **runtime panic**, not a silently skipped language.
There is no skip path to fall back to: the app loads the precompiled
`dump-load` bundle (`default_newlines.packdump`), so syntect's YAML pre-test
(`yaml_load.rs::try_compile_regex`) never runs at runtime.

The whole default syntax set was swept under both feature sets and the output
was compared byte for byte:

| Measure | Before (onig) | After (fancy-regex) |
|---|---:|---:|
| grammars | 75 | 75 |
| themes | 7 | 7 |
| regexes compiled | 8 156 | 8 156 |
| regexes that fail to compile | 0 | 0 |
| grammars that panic when highlighted | 0 | 0 |

The sweep compiles every regex of every grammar with the active engine and
then highlights a sample in every grammar under `catch_unwind`, so the panic
path is exercised, not inferred. The two outputs are byte-identical.

### R3. Checked and dismissed — do not spend time on these

| Candidate | Why it was dropped |
|---|---|
| `reqwest` `charset` feature → `encoding_rs` (36.3 kB) | `encoding_rs` is **also** pulled in by `tauri-plugin-shell`, so dropping reqwest's charset saves nothing |
| `tauri` `features = ["devtools"]` | measured: only **7 symbols** in the whole binary mention devtools — negligible |
| `git2` default features (ssh/https) | already off: `Cargo.lock` shows git2 depends only on `bitflags`, `libc`, `libgit2-sys`, `log` — no openssl, no curl |
| `tokio` `features = ["full"]` | tokio is 103.8 kB total, and the app genuinely uses `net`, `process`, `sync`, `time`; trimming `signal`/`fs` saves little and risks Tauri's feature unification |
| `ts-rs` in `[dependencies]` | it is only needed to emit `.ts` files during `cargo test`, so it belongs in `[dev-dependencies]` — but its runtime `TS` impls are generic and land inside `buildmesh_lib`'s 13.2 MB, so the size win is negligible. Worth fixing for correctness, not for size |
| `rusqlite` `bundled` (1 410.7 kB) | inherent to shipping an embedded database; a system SQLite or a pure-Rust engine is a major change, not a trim |
| `libgit2-sys` (909.0 kB) | inherent to the git feature set |
| Consolidating the two HTTP stacks | `reqwest`+`rustls`+`h2`+`ring` ≈ 1.7 MB **and** the app's own `tiny_http` + `tokio-tungstenite` server coexist. Merging them is a real project, not a low-impact trim |

### R4. What would actually move the binary

Only removing code helps here, and the app's own code is 62 % of the binary.
The realistic levers, in order of payoff:

1. Feature-gate the subsystems that a given install never uses — the
   LAN/remote-access server (`http/` + `tiny_http` + `tokio-tungstenite`),
   the companion tool runner, the circuit worker — behind Cargo features so
   release builds can omit them. This is the only path to a materially
   smaller `.exe`, and it is a substantial refactor.
2. R1 and R2 — **done**, net −689 152 bytes on the release binary.
3. `lto = "thin"` → `lto = "fat"` in `[profile.release]` trades build time for
   size; `codegen-units = 16` → `1` does the same. Neither was measured here.

## Limits of this analysis

- Frontend deltas are measured on the **desktop** entry chunk. The mobile
  bundle (`dist/mobile`, 816 kB → 818 kB) is a separate entry; it was rebuilt
  but not re-analysed per chunk.
- The Rust figures come from one Windows x86-64 release build. macOS and Linux
  binaries have different C library content (no libgit2/sqlite difference, but
  `zbus` enters the tree on Linux through `tauri-plugin-opener`), so the
  per-crate table does not transfer unchanged.
- Symbol sizes are derived from linker-map address deltas, which include
  padding and exclude COMDATs the linker discarded; they are accurate to a few
  percent, not to the byte.
- The R1/R2 binary delta (−689 152 bytes) is the *net* of the two changes
  together. It was not split into a per-change figure, because the two release
  builds that isolate them differ by one dependency feature each and a
  separate measurement pair per change costs another two release builds.
- The release binary was measured against a `dist/` that also contained
  Vite sourcemaps. Both sides of the comparison had them, so the delta is
  valid, but the absolute sizes are larger than a shipping build's.
- The Rust binary size was *not* re-measured after the frontend split landed,
  so the executable figure above reflects the dependency trims only.
- `fancy-regex` implements a subset of Oniguruma. syntect compiles a grammar's
  regexes lazily and `.expect()`s on failure, so a rejected pattern is a
  **runtime panic**, not a silently skipped language — the risk is a crash in
  the diff view, not a missing colour. The default syntax set was swept under
  both feature sets (75 grammars, 7 themes, 8 156 regexes, 0 compile failures,
  0 panics, byte-identical output), so the shipped grammar set is not affected.
  A *future* grammar that used an unsupported construct would need its pattern
  checked before it ships.

## Reproducing

The helper scripts used here are throwaway analysis tools, not repository
gates: they live untracked in `.tmp/` and are not part of the build. The
method they implement is described under "Scope and method" above.

```powershell
# Frontend composition and reachability
npm run harness -- link-deps
npx vite build --sourcemap
node .tmp\bundle-analyze.mjs dist packages   # bytes per package, per chunk
node .tmp\chunk-graph.mjs                     # eager vs lazy chunk totals
node .tmp\measure.mjs                         # first-load raw + gzip totals

# Rust per-crate attribution
$env:CARGO_TARGET_DIR = "<worktree>\src-tauri\target"
$env:TS_RS_EXPORT_DIR  = "<worktree>\.tmp\ts-rs-export"
cargo rustc --release --bin buildmesh -- `
  -C link-arg=/MAP:<worktree>\.tmp\buildmesh.map
node .tmp\rust-crate-sizes.mjs .tmp\buildmesh.map
```

The verified frontend patch is in `.tmp\lazy-boundaries.patch` and is also
written out in full above.
