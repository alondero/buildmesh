# 28. Circuit-Run Capacity Contract (split per-mesh capacity into run-admission + agent-slot backstop)

Status: accepted

The Autopilot Circuits scheduler (issue #1467, walking skeletons #1205/#1206)
previously enforced per-mesh capacity through a single column,
`meshes.autopilot_concurrency_limit`, which counted **distinct piloted
agent nodes** attached to active circuit runs. This caused a deadlock
when two PR-review runs overlapped on one mesh: each implementation agent
stayed attached to receive review feedback, both agent slots were
occupied, and the downstream reviewer step was parked in `pending_slot`
until the implementer's slot freed — which never happened unless the
user intervened.

## Context

`docs/knowledge-primer.md:319` flagged this exact gap as "per-run only
until the multi-run scheduler milestone", and `docs/specs/prd-autopilot-mode.md:37`
defined `autopilot_concurrency_limit` as a per-mesh agent cap. Issue #1467
is that "multi-run scheduler milestone".

A circuit run is a graph of nodes (spawn / inject / notify / gate / close);
each `SpawnAgentNode` consumes a mesh-level **agent slot** for as long as
the spawned agent node is referenced by a running or paused step. Review
blueprints (issue-driven Autopilot review) keep the implementation agent
attached throughout the PR-review cycle so they can receive targeted
feedback. Two overlapping review runs therefore saturate the per-mesh
agent cap with implementation agents alone, leaving no room for the
reviewer spawn.

The `autopilot_circuits.concurrency_limit` column, currently defaulting
to 1, is a **per-circuit running-step budget**, not a run cap. It bounds
how many `SpawnAgentNode`/`InjectPty` steps run simultaneously across a
single circuit's `running`/`paused` runs — distinct from the new
mesh-level run cap.

Three alternatives were considered:

1. **Per-circuit run cap** (e.g. `autopilot_circuits.max_concurrent_runs`).
   Pros: locality, the cap moves with the circuit definition. Cons: the
   deadlock is mesh-scoped (two PR-review loops on DIFFERENT circuits
   collide), so a per-circuit cap doesn't prevent it. User explicitly
   required a mesh-level contract.
2. **App-wide global pool** (extend the existing
   `autopilot_pool_size`). Pros: simplest mental model — one number
   covers everything. Cons: hides the structural difference between
   "max agents across the whole app" (legacy pool) and "max concurrent
   circuits on this mesh" (run admission). Mixing them would have
   silently changed legacy behaviour for everyone who set a pool size
   today.
3. **Keep the legacy column unchanged; add a separate column.**
   Pros: matches the user's "do not silently change legacy autopilot
   semantics" requirement; preserves the global pool as a separate
   backstop; cleanly distinguishes circuit admission from the safety
   limit. Cons: one more column on the `meshes` table.

We chose (3).

## Decision

**Storage.** New mesh column `meshes.circuit_run_capacity INTEGER NOT
NULL DEFAULT 2` (schema v36). Range `1..=8`, validated at the IPC
boundary (`update_mesh_circuit_run_capacity`), mirroring the legacy
column's clamp. Default `2` directly unlocks the acceptance criterion
"two concurrent runs as expected configuration" out of the box.

**Wire type.** `i32` (mirrors `autopilot_concurrency_limit`), so the
field reaches the TS frontend through the standard ts-rs generation
pipeline (`src/types/generated/Mesh.ts`, `MeshRow.ts`). Regenerated by
`cargo test`; CI gates via `git diff --exit-code src/types/generated`.

**Admission unit.** **One capacity unit per admitted run** — a run in
state `running` or `paused`. `pending` does NOT count: counting
`pending` would self-deadlock (every pending run's count read would
see itself + peers, so `count < cap` is always false and no run ever
admits). Terminal runs (`completed` / `failed`) do NOT count; a release
through `db::release_circuit_run` transitions the row out of the
admitted set in a single UPDATE.

**Where the gate lives.** The pure stepper operates on one `RunView`
and cannot see mesh-level capacity; the gate lives in the impure seam
(`services::circuit_worker::run_pass`). A new helper
`may_admit_run(active, mesh)` is called inside `run_pass`'s iteration
loop: for each `pending` run, we check `count_active_circuit_runs(mesh_id)
< circuit_run_capacity`; if full, defer the run's `Triggered` event to
the next pass. The run stays `pending` in the DB — no separate queued
table is needed. The worker has a mesh-id cache so a mesh with N
pending runs but only 1 row read is the common case.

**Fairness.** `db::list_active_circuit_runs()` orders results by
`r.id` (auto-incrementing), which is FIFO by insertion. A later
implementation run cannot starve an earlier reviewer step because:
(a) the gate is per-mesh (cap bounds the mesh, not the circuit),
(b) iteration order is FIFO, (c) the cap is exact (not weighted).
A paused run **retains** its slot per the user-chosen semantics in the
#1467 planning conversation — pause preserves the in-flight agents so
resume continues cleanly, matching the pre-existing
`paused_runs_stay_active_and_counters_count_them` invariant.

**Backward compatibility.** `meshes.autopilot_concurrency_limit` is
UNCHANGED. The legacy Autopilot poller (`services::autopilot.rs:326`)
keeps reading it via `effective_capacity`. The circuit worker stops
reading it for run admission; it continues reading it only to feed
`mesh_agent_free_slots` — the existing agent-slot backstop. The
breakdown is documented in `docs/knowledge-primer.md`'s Autopilot
section so future contributors don't re-merge the two semantics.

**Single-release idempotency** lives at the canonical state-change
site — `db::commit_circuit_advance`'s run-state branch. When `run_state`
is `Some(completed|failed|cancelled)` (per `is_terminal_run_state`),
the UPDATE uses a `WHERE state IN ('pending', 'running', 'paused')`
filter; a row already in a terminal state matches zero rows, the
UPDATE is a no-op, and **no** capacity is double-decremented. Three
failure modes this guards against:

1. **Concurrent terminal writes** — the stepper's
   `finish_run_if_done` flushing `completed` racing an effect-failure
   path to `failed`. The first commit wins.
2. **Crash after commit, before wake** — the next worker pass retries
   the wake cleanly without re-emitting `Released`.
3. **Retry path** — a `RetryLimit` reseting a failed step keeps the
   run's terminal state untouched (the WHERE filter blocks the
   reschedule from clobbering it).

On a successful terminal commit (`rows_updated > 0`), the function
wakes the circuit worker so the next pass promotes the next FIFO
pending run. Wakes are idempotent (condvar-only). All terminal
transitions — whether from the stepper, the effect-failure path, or
a future cancel IPC — land at this single atomic write site, so
there is no parallel "release" helper to keep in sync.

**UI surface.** New sibling Field "Max concurrent circuit runs" in the
Autopilot Probe tab (issue #1013's home for Autopilot policy), placed
next to the existing "Max concurrent autopilot nodes" field. Persisted
via a narrow IPC `update_mesh_circuit_run_capacity(mesh_id, capacity)`
that writes ONLY `circuit_run_capacity` — the five-column atomic
`update_mesh_autopilot` write stays intact so toggling the run cap
can't clobber the user's autopilot policy.

## Consequences

- Two-overlap PR-review flows (the deadlock scenario) no longer park
  reviewer steps in `pending_slot` indefinitely. With
  `circuit_run_capacity = 2`, two PR-review runs can each spawn their
  implementation + reviewer agents without reviewer admission depending
  on the other run's agent-node count.
- A third run on the same mesh is held at the circuit-run boundary
  while two are admitted. It stays `pending` and is admitted FIFO when
  the first run reaches a terminal state.
- Capacity is released exactly once when a run reaches a terminal
  state (including failure and crash-recovery paths through
  `release_circuit_run`).
- `pending_slot` retains its existing vocabulary meaning — a *step*
  status, not a *run* status. A *run* sitting at the run-admission
  gate has its `state = 'pending'` (the row's state column, NOT
  a step's status).
- The legacy `autopilot_concurrency_limit` is preserved unchanged for
  the legacy Autopilot pool, with its separate label and its separate
  semantics. UI text disambiguates the two: "Max concurrent autopilot
  nodes" (legacy) vs "Max concurrent circuit runs" (new).

## Out of scope

- Renaming `pending_slot` to a more descriptive string (load-bearing
  vocabulary across 5 files; separate concern).
- Sub-run priority / weighted round-robin across circuits (no fairness
  UX signal today; FIFO by insertion is what #1467 asks for).
- Per-circuit mutable `concurrency_limit` IPC (the value stays a
  create-time-only field per the existing API contract).
