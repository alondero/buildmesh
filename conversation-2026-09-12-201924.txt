◆ Review: PR #1737 — feat(transcript): add Muse transcript reader

  Revision under review: 20ea84cb95d0a2fbf18169f79440257491d2714f (branch
  pr1737-feattranscript-add-muse-transcript-reader-i, clean tree, single commit
  on top of 25ccf92d). Previous findings: none — the PR has zero comments and
  zero reviews, so there is nothing to re-check.

  This is a well-constructed change: the registry-seam wiring is genuinely three
  lines, the parser mirrors Claude Code's coalescing discipline faithfully, the
  privacy skip for reasoning_committed is correct and tested, and the inventory
  pins fail closed in both Rust and TS. But there are two actionable defects.
  Verdict: request changes.

  Finding 1 (actionable, correctness): indexed session_log_path is never
  host-translated

  src-tauri/src/services/transcript_reader/adapters/muse.rs:159 —
  muse_locator_in returns the raw guest path from session-index.db straight into
  locate() (src-tauri/src/services/transcript_reader/adapters/muse.rs:91), which
  flows untranslated into path.exists() / File::open in read_tail.

  Three pieces of in-repo evidence say this is wrong:

  • The sibling does it:
    src-tauri/src/services/transcript_reader/adapters/agy.rs:35 wraps its
    resolved home in env::to_host_path. Your adapter is documented as "same
    approach as the AGY adapter" but skips this step.
  • The same database column is translated one file over: find_session in
    src-tauri/src/agent/provider/adapters/muse.rs:172 calls
    crate::env::to_host_path(&path) on every row before opening it.
  • Your own docstring (lines 152–158) admits it: "on Windows the caller must
    wrap it in to_host_path". But the actual caller — locate_transcript →
    read_tail_from_file — never does. A docstring that assigns responsibility to
    a caller that doesn't accept it is a bug with a comment on top.

  Impact today is latent, not live: available_on is [Linux, Macos], and
  to_host_path is the identity function on those hosts, so native Linux/macOS
  reads work. But it violates the hard rule (never pass Linux/WSL paths to
  Windows-side APIs) and breaks the moment muse is offered on a Windows+WSL host
  — the exact deployment the cli_dir_for_spawn / to_host_path machinery in this
  file was built for. Fix is one line in muse_locator_in or locate(), mirroring
  agy.rs:35. While you're at it, resolve the contradiction: either translate
  inside the helper (preferred — matches both siblings) or delete the misleading
  docstring paragraph.

  Finding 2 (actionable, spec/docs): catalogue prose now disagrees with the code

  • src-tauri/src/services/transcript_reader/mod.rs:8 says "Eight harness
    formats are supported" but enumerates seven — Muse is missing from the list
    (Claude, Cursor, Codex, Antigravity, Grok, Command Code, OpenCode).
  • docs/knowledge-primer.md (~line 329) lists the wired-reader providers as
    "(Anthropic/Claude-compatible profiles, Codex, Cursor, AGY, Grok, Command
    Code)" — no Muse. Your capabilities.rs test comment explicitly claims the
    pin "must match the matrix documented in docs/knowledge-primer.md". The
    matrix now disagrees with the pin. Add Muse to both lists.

  Non-blocking question: started+prompt fallback can double-count

  parse_muse_turns treats both user_prompt_display and started-with-prompt as
  user turns with no dedup. The commit message says some sessions emit "a bare
  started first then a user_prompt_display" — if "bare" truly means prompt-less,
  the else { continue } arm already handles it and there's no double. But if any
  session emits started carrying the prompt and the display event for the same
  prompt, you get two identical user turns. I have no live evidence either way,
  so this isn't a change-request — but either cite the live shape proving
  they're mutually exclusive or note it as a known limitation.
